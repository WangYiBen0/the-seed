# [TheSeed] 镜像工具 Benchmark（宏 + 倍速）

> 本文档给出镜像工具的跑分方法与样例数据。所有数据都在**未修改任何游戏源码**
> 的前提下测得：倍速通过重排 `requestAnimationFrame` 的虚拟时间戳实现，
> 宏/自动挂机通过游戏自己的公开输入状态（`Input`）与 DOM 事件驱动。

## 1. 三种基准

| 场景 | 内容 | 关键指标 |
|---|---|---|
| `throughput` | 在一局真实对局中，×8 倍速连续跑 N 秒（性能模式：粒子 15%、关特效、无帧率上限） | `tps`（每真实秒的模拟帧数）、`ratio`（游戏秒/真实秒） |
| `macro` | 回放内置"站桩 30s"操作宏（按住攻击 + 绕圈瞄准），×4 倍速 | `ratio`（宏时间轴对齐精度）、击杀/伤害 |
| `fullrun` | 自动挂机（全自动模式）从新档打到目标无尽深度 | 深度、击杀、受击、结局、真实耗时 |

面板入口：`基准 · BENCHMARK` 三个按钮；命令行入口：

```bash
nix run .#bench -- --kind throughput --seconds 8 --speed 8
nix run .#bench -- --kind macro      --seconds 15 --speed 4
nix run .#bench -- --kind fullrun --seed 7 --policy bloom --goal-depth 1 --speed 8 --timeout 300
```

每次运行输出一行 JSON（`TSW_RESULT …`），`--out results.jsonl` 可追加落盘。

## 2. 样例数据（本机：NixOS，headless Chromium 155，软件渲染）

### 吞吐（throughput）

```json
{"kind":"throughput","speed":8,"seconds":6,"ticks":2879,"tps":479.7,
 "gameS":48,"ratio":8,"inRun":true,"ua":"Chrome/155.0.0.0"}
```

- ×8 档理论值 = 8 × 60 = **480 ticks/s**，实测 **479.7**，误差 < 0.1%；
- `ratio = 8.00`：游戏内时间与真实时间严格 1:8。

### 宏 + 倍速（macro）

```json
{"kind":"macro","speed":4,"seconds":15,"macro":"hold-attack",
 "gameS":25.1,"wall":6.3,"ratio":4,"kills":0,"dmg":0,"ua":"Chrome/155.0.0.0"}
```

- 宏按**虚拟时间轴**录制，回放时与游戏时间严格对齐（`ratio = 4.00`）；
- 站桩宏在起始房没有敌人，所以 kills/dmg 为 0 —— 这是预期行为；
  要测战斗表现请用 `fullrun`。

### 全自动一局（fullrun）

样例（bloom 策略、seed 7、×8、目标无尽 1 层）：

```json
{"kind":"fullrun","speed":8,"seed":7,"policy":"bloom","goalDepth":1,
 "end":"death","gameT":117,"floor":0,"kills":74,"hits":25,"dmg":2570,
 "weapons":["nail"],"shards":{"stat":1,"rnova":1,"rico":1,"fury":1},"syn":0}
```

自动挂机的走位/拿卡策略是"可用"水平，不是人类上限 —— **数据用于策略横向
对比（选卡倾向、武器偏好），不代表任何"人类天花板"**。多次运行的矩阵
（4 策略 × 2 种子）见第 4 节。

> **Firefox 支持**：2026-10-18 已在 headless Firefox 158 验证完整链路——
> boot → 起名 → 选难度 → 自动挂机一整局（`ua: Firefox/158.0`，kills>0）。
> 游戏与全部工具在 Chrome / Edge / Firefox 下均可运行。

## 3. 方法论说明（为什么这些数字可信）

1. **倍速不靠改游戏**：`tools/core.js` 在游戏启动前替换
   `window.requestAnimationFrame`，把虚拟时间戳按倍率推进；游戏的
   `frame(now)` 只看到时间戳，模拟与渲染节拍完全不变。
2. **宏不靠改游戏**：回放重新派发真实 DOM 事件（KeyboardEvent/MouseEvent），
   走的是引擎自己的监听器；坐标按画布矩形换算，分辨率无关。
3. **可复现性**：`TSW.rng.seed(n)` 用 mulberry32 替换 `Math.random`，
   同一 seed 的 fullrun 从洗牌到掉落完全一致。
4. **性能模式只动视觉**：`QS.part/fx/fps`、`SET.shake/flash` 是渲染质量参数，
   不触碰任何游戏数值。

## 4. 构建对比（probe：构造存档 → 模拟无尽深度）

`fullrun` 测的是"挂机从零打到无尽"的全流程；要单独比较**构建（build）**，
用 `probe`：它构造一份带指定武器/血清/芯片的运行存档（走游戏自己的
`loadSave` 校验，不改任何源码），把游戏投放到第 5 章 + 模拟无尽深度，
然后让自动挂机打 N 游戏秒，输出战斗时间归一化的击杀/伤害速率：

```bash
node scripts/headless-bench.mjs --kind probe --depth 5 --seconds 90 --seed 7 \
  --speed 8 --build '{"weapons":["rail"],"wlv":{"rail":3},"shards":{"keen":4,"heavy":5}}'
```

### 深度 5 · 同 seed 对比（自动挂机，战斗时间内归一化）

| build | 击杀/分 | 伤害/分 |
|---|---|---|
| rail + keen4/heavy5/frenzy5/needle3（满锻造） | **54.0** | **1194** |
| nail 裸装 | 40.5 | 825 |
| hail + bloom3/shrap3/ember/fury/leech | 31.4 | 723 |

**结论**（详见 `endless-guide.md`）：高面板武器 + 冻结期输出血清 > 低面板
高频武器硬灌引爆链；bloom 引爆是唯一随深度放大的伤害，但起爆仍靠武器 DPS。
挂机所方差较大（导航/走位占一半因素），精确结论以多 seed 中位数为准。

## 6. 躲弹幕测评（dodge benchmark）

专门测"闪避"这一项能力，而不是整局综合强度。做法：**禁止开火**（`noFire`），
让敌人不会减少，再按固定节拍**持续补充远程敌人**（gunner/sniper/turret/mortar，
保底 7 个），于是弹幕只会越来越密 —— 这是一场纯挨打压力测试。

指标：

| 指标 | 含义 | 方向 |
|---|---|---|
| `hitsPerMin` | 受击次数 / 游戏分钟 | 越低越好 |
| `dangerAvg` | 站位处威胁值均值（预警圈+弹道预测+虚空区+地刺） | 越低越好 |
| `hazardPct` | 威胁值 ≥1.2 的 tick 占比（暴露率） | 越低越好 |
| `clearAvg` / `clearP5` / `clearMin` | 所选方向上"最坏一枚子弹"的横向余量（均值 / 5% 分位 / 最小值） | 越高越好 |
| `dashesPerMin` | 冲刺频率 | 参考 |

归一化用**实测 play tick 数**（`ticks/3600 = 游戏分钟`），而不是 `G.runT`——
后者在自动重开时会归零，早期版本用它算出了 4440 次/分的荒谬数字。

| 种子 | v2 受击/分 | v1 受击/分 | v2 危险值 | v1 危险值 | 胜 |
|---|---|---|---|---|---|
| 11 | **15.1** | 22.2 | 4.138 | 1.698 | v2 |
| 23 | 22.4 | **22.0** | 3.356 | 5.68 | v1 |
| 41 | **9.2** | 21.2 | 0.734 | 3.367 | v2 |
| **平均** | **15.6** | 21.8 | — | — | — |

- 三个有效种子中 v2 赢 2 个（平均 **15.6 vs 21.8** 次/分，约 **-29%**）；种子上限只有 3 个，
  单种子可翻转，所以结论按平均值看，不要当成显著性证明；
- 来源：v2 把"最坏一枚子弹的横向余量"（`laneClear`）算进评分，避免两侧同时被夹，

## 9. 实力期望与方差（5 种子实测）

同配置（bloom 流派 · classic · 目标无尽 1 层 · ×8 倍速 · 全自动）跑 seed 11/23/41/57/73：

| 指标 | 均值 | 标准差 | 最差 | 最好 |
|---|---|---|---|---|
| 存活（游戏秒） | 267 | ±81（CV 30%） | 163 | 389 |
| 击杀 | 41.2 | ±14.4（CV 35%） | 21 | 59 |

- 方差主要来自**开局房间构成与掉落**：拿到能配合的血清（bloom/shrap/frenzy）就滚起来，
  拿不到就死在第一章；
- 另有两个种子触发了 `stall`/`replan` 计数（4/14 与 8/25），即仍有少量绕圈重算，
  但都被兜住（没有卡死：两局都正常推进到死亡）；
- 复现：

```bash
for s in 11 23 41 57 73; do
  node scripts/headless-bench.mjs --kind fullrun --seed $s --policy bloom \
    --goal-depth 1 --speed 8 --timeout 200 --out .tmp/var.jsonl
done
```

跑多局会额外输出一行 `{"kind":"summary", ...}`（均值/标准差），便于对比改动效果。

### 被数据否掉的方差假设（留档，避免重复踩）

| 假设 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 开局先堆生存能压方差 | 首层且血清 <2 时，plate/vital/quick/swift/leech 权重 ×1.45 | seed 23/41/57 的 gameT 264/251/268 → **200/206/173**，击杀 40/36/59 → **25/31/8** | **否**：标准差从 80 降到 18，但均值塌了——"稳定地更差"，已回滚 |

原因分析：首层防御血清挤压了输出位，清怪变慢 → 房间拖长 → 弹幕叠满，反而更容易死。
下一个该试的方向是**反方向**（首层 DPS 偏向）或直接治理"清怪速度"而非生存。

## 10. 绝境五锁基线（目标①的起点）

五个修饰符全开：`rage`（敌人攻击频率 ×2）、`deathfight`（致命伤后 2 秒不可选中）、
`bulwark`（敌人进战后 20 秒减伤 20%）、`rot`（免疫燃烧/中毒/冰冻）、`cyst`（敌人生命上限 +25%）。

**怎么让修饰符进入基准局**（踩过三个坑，记下来）：

1. `modifiers.js` 的 `PENDING_MODIFIERS` 是它自己作用域里的 `let`，bench 里赋值只会遮蔽，
   改不到游戏；`sortie()` 又会走营地而不是直接开局。
2. 正解是**构造存档**：`{v:1, floor:0, diff:'despair', modifiers:[五锁], …}` → 交给游戏自己的
   `loadSave()` → `cleanModifiers(s.modifiers, s.diff)` 校验 → `resumeRun()`。
3. `STORE.setItem` 在 `STORE.locked` 时会**静默丢写**，必须直写 `STORE.mem` + `dirty`。
4. `whenGame()` 只等 `game.js`（脚本序号 25/76），而 `newRun()` 里调用 `takeRunModifiers()`
   定义在 `modifiers.js`（序号 70/76）→ 开局太早会 `ReferenceError`。基准必须先等脚本就绪。

结果行会回显 `modifiers: [...]`（开局）与 `modifiersAtEnd`，可据此确认五锁真的生效。

### 三轮迭代（seed 7 / 23 / 41，rounded，×8，各 150 秒，同种子同配置）

| 种子 | 原始基线 T/kills | +死斗识别 T/kills | +清房追击 T/kills |
|---|---|---|---|
| 7 | 198 / 9 | 158 / 15 | **357 / 21** |
| 23 | 136 / 11 | 267 / 17 | **255 / 25** |
| 41 | 111 / 86 | 389 / 59 | **357 / 112** |
| **均值** | **148 / 35.3** | 271 / 30.3 | **323 / 52.7** |

**两处改动**（都在 `tools/auto.js`，未动上游）：

1. **死斗敌人当危险源**：绝境「死斗」修饰符下，`deathFightLeft > 0` 的敌人**不可选中但仍每帧造成接触伤害**
   （`enemies.js:115` 没有过滤它）。原来挂机在 `nearestEnemy` 里把它们整个跳过 → 站在它们旁边挨打却不躲。
   现在不瞄准它，但纳入威胁场驱离。存活 **148 → 271 秒**。
2. **清房追击**：房间清空条件是无未死敌人（`game.js:229`），只要有一个漏网的（躲墙后、`rot` 免疫 DoT、
   够不到）整局就停摆。实测探针看到「敌人只剩 1 个、击杀数 50 秒不动」。
   现在：房间激活但**没有可射击目标**时，0.5 秒后主动朝最近敌人逼近。
   存活 271 → **323 秒**，击杀 30 → **53**。

两处都是**存活与击杀同向改善**（不是拿命换输出），所以是实质进步。

**试过但未采纳的变体（留档）**：把「直追」升级成「BFS 绕到能射到的格子」

| 变体 | 3 种子均值 |
|---|---|
| 直追（采纳） | 323s / 52.7 杀 |
| 纯绕路（每 0.9s 重算） | 230s / 52.7 杀 ← 明显变差 |
| 卡住才绕（1.2s 无进展才 BFS） | 284s / 54.7 杀 ← 落在 ±30% 噪声内，无法证实 |

单局方差 CV≈30%，这种量级必须多种子且差距显著才算数；绕路会打断瞄准/DPS，
所以保留直追。

**另一条未采纳**：门框卡位加「3 秒无击杀就主动出击」

| 变体 | 3 种子均值 |
|---|---|
| 无限卡门（采纳） | 323s / 52.7 杀 |
| 3s 超时出击 | 244s / 37.3 杀 ← 均值下降，回退 |

探针确实看到单只精英卡门 32 秒（`doorfunnel`、击杀冻结），但在绝境里卡门
本身是**生存手段**：放弃则会同时面对多个敌人，存活掉得更快。
所以「卡门太久」的诊断是对的，但解法不是取消卡门。
原始数据：`docs/data/despair-fivelock.jsonl`。

## 11. 入侵抵抗基线（目标②的起点）

入侵抵抗（`RUN_MODE='invade'`）是 Brotato 式竞技场：20 波、最多 6 把武器自动开火、
波间有商店/补给/升级。**挂机不认识它的界面状态**（`ivrole` / `ivstart` / `ivlv` /
`ivcrate` / `ivshop`，统称 `IV_UI`），所以直接开局会软锁。

**能测起来的最小通道**（`--kind invade`）：

1. 构造 `achroma_ivrun` 存档（`{v:1, diff, iv:{wave, role, w:[{id,t}], …}}`），
   字段由游戏自己的 `ivLoadSave()` 逐项校验（`wave` 1..19、`role` ∈ `IV_ROLES`、
   `w[i].id` ∈ `IV_W`、`t` 0..3）。
2. 直写 `STORE.mem`（`STORE.setItem` 在 `locked` 时静默丢写）→ `ivResume()`。
3. `ivResume()` 结束后 `G.state='ivshop'`；用游戏自己的 `ivNextWave()` 进战斗，
   状态路径会打印成 `ivshop → play`。
4. 关掉 `autoRestart`，否则死亡会被自动重开，样本变脏。

**结论**：绝境入侵下挂机稳定卡在**第 6 波**（起始第 5 波＝撑过 1 波多），
三颗种子一致，说明这是结构性瓶颈而不是随机波动。目标②的起点就是 6 波 / 20 波。

### 五锁的真实瓶颈（探针实测，2026-10-27）

对 seed 7 做了逐帧探针（每 2 秒采样），一条典型局的轨迹：

| 游戏秒 | 护甲 | 血 | 击杀 | 场上敌人 | 状态 |
|---|---|---|---|---|---|
| 44–76 | 3 | 5 | **9（冻结 32 秒）** | 1（精英，距离 >60） | `doorfunnel` |
| 83–111 | 3→1→2→3 | 5 | 10→21 | 最多 6 | 正常交火 |
| 118 | 3 | 5 | 21 | 0 | 选卡 |
| 130–144 | 3 | 5 | 22→23 | 1–4 | 继续 |

两条硬结论：

1. **血几乎不掉，护甲在反复吸收**（`hits` 缓慢上升但 `hp` 一直是 5）——
   说明死因不是「被磨死」，而是**清不完**（波次/房间拖住）。
2. **全程只有一把 `nail`、零血清**（`sh:0` 直到 t≈122）——
   `bulwark`（敌受伤 -20%）+ `cyst`（血量 +25%）双重压制下，
   初始钉枪 DPS 完全磨不动，这才是卡住的根因。

对应地，本轮试的两条「减少空等」的改动都被数据否决（见上）：
问题不在等待策略，而在**输出不足**。下一轮方向：让挂机在绝境里**优先确保拿到输出型血清/更好武器**
（而不是继续磨），必要时把「清不动就换目标去拿资源」作为一等策略。

## 12. 方法论纠错：3 个种子不足以判定改动（重要）

前面几轮我用 **seed 7/23/41（3 个种子）** 做前后对比，并据此宣布过
「148s → 323s 是实质进步」。把种子扩到 6 个重测同一配置后：

| 配置 | n=3 均值 | n=6 均值 |
|---|---|---|
| 五锁基线（当前代码） | 323s / 52.7 杀 | **214 ± 70s / 40.7 ± 47.7 杀** |

**n=3 的 323s 是高估了 50% 的抽样结果**。按 n=6 的标准差计算：

> 单局 gameT 标准差 70s，n=6 的 95% 检测下限 ≈ **79 秒**。
> 也就是说，任何小于 ~80 秒（约 37%）的均值差异，用 6 个种子**根本测不出来**。

### 这条纠错带来的操作规则

1. **改动验收至少 6 个种子**（7/23/41/57/73/91），并且要和同批次重测的对照组比，
   不能和跨批次的历史数字比（批次间环境/负载也不同）。
2. 报告必须带 **± 标准差** 和样本数，不给单点数字。
3. 一次跑 3 个种子得到的“提升”只能当**方向性信号**，不能当结论——
   本文件 §10 里被否决的三个微优化，和“被采纳”的那次，都要按这条重新理解。
4. 想检测 <20% 的改动，n 需要 20+；单局约 50 秒真实时间，即一次 A/B 约 20 分钟。

原始数据：`docs/data/despair-fivelock-6seed.jsonl`（6 行，含每种子明细）。

## 13. 零位移死局与导航硬兜底（含 6 种子结果）

### 症状（seed 91 复现）

用调试镜像（`?trace=1` 时每 3 游戏秒打印 `TSW.auto.dbg`）看到一局**完全停下**：

```
 "px":1023,"py":1386, "vial":809, "wp":[216,1448], "note":""}
```

1. `pickObjective` / `drivePlay` 增加 **WORLD 就绪守卫**（地形未生成时不追目标）；
2. **导航硬兜底**：导航状态下若 **2.5 秒零位移**，强制沿一个 pit/void 安全的方向
   冲 1.2 秒（计入 `stall` 指标），打破死局。

- 存活 +45s **低于 79s 检测下限，统计上不显著**；

## 14. 基准是非确定性的（决定性发现，推翻前面所有 A/B 的精度）

**实测**：同一个种子（91）连续跑三次，配置完全相同：

| 次 | 游戏秒 | 击杀 | stall |
|---|---|---|---|
| 1 | 147 | 0 | 56 |
| 2 | 296 | 28 | 49 |
| 3 | 461 | 30 | 52 |

**同一 seed 差 3 倍**。原因在 `site/js/game.js:693`：

```js
const rdt = Math.min(.05, Math.max(0, (now - last) / 1000)); last = now;
```

每帧的 `dt` 来自**真实经过时间**，而游戏里所有积分型逻辑
（`p.vx = lerp(p.vx, mx*spd, Math.min(1, dt*14))`、弹道、AI 转向、相机）都依赖它。
倍速工具只是让每帧步进变快，**并不会把 `dt` 固定**。

`TSW.rng.seed()` 只替换了 `Math.random`（覆盖 265 处调用），
所以**随机数可复现，物理不可复现**。

### 这推翻了什么

- §12 的「6 种子检测下限 79 秒」只在**同批次同负载**下成立；
- 所有跨轮次 A/B（包括我宣布过的「148s → 323s」「214 → 259」）都不可比，
  因为它们跨了批次、负载也不同；
- 想得到可比数字，必须**同一批次内交错跑对照组与实验组**（A/B/A/B…），
  并且报告同批次的相对差值，而不是跨批次均值。

### 正确的测量协议（后续必须遵守）

1. 一次会话内，**交错**跑 `baseline, candidate, baseline, candidate, …`
   各 N 局（N≥5），用**配对差**的均值和标准差判断；
2. 每组前后必须**同机同负载**（不要一边跑基准一边做别的事）；
3 报告 `配对差均值 ± 标准差`，而不是两个独立均值；
4. 想要 20% 精度，配对差样本需要 ~15 对以上。

在没做到这些之前，任何「提升 X%」都只能算**传闻**，不算结论。

## 15. 配对 A/B 工具与第一批结论（`--kind ab`）

按 §14 的协议实现了 `--kind ab`：**同一浏览器会话内交错跑 A/B/A/B…**，
输出配对差 ± 标准差、SEM、95% 置信区间、t 值和判定。

```bash
nix run .#bench -- --kind ab --rounds 5 --diff despair \
  --mods rage,deathfight,bulwark,rot,cyst --speed 8 --seconds 15 --timeout 70 \
  --optA '{"autoOpts":{"navFallback":false}}' \
  --optB '{"autoOpts":{"navFallback":true}}'
```

`--optA/--optB` 是 JSON，`autoOpts` 会临时覆盖 `TSW.auto.opts` 的同名项并自动还原。

### 第一个结论：导航兜底**无效**（推翻上一轮的 +45s）

| 指标 | 值 |
|---|---|
| A（兜底关）均值 | 223 秒 |
| B（兜底开）均值 | 232 秒 |
| **配对差** | **+9.2 ± 83.6**（SEM 37.4） |
| 95% CI | **[-64.1, +82.5]** ← 横跨 0 |
| t | 0.25 |
| 判定 | **无显著差异** |
| 击杀配对差 | -43.8（配对差极大，逐对看正负都有） |

**上一轮用 6 个独立种子得出「214 → 259 秒」，在配对测量下不成立。**
原因正是 §14 说的：独立样本的方差里混入了批次/负载差异，配对测量把它抵消了，
于是看到「兜底对存活几乎没有作用」。

### 这条结论的意义

- 兜底值不值得保留？**它不伤**（CI 横跨 0），而且能解开「零位移死局」这类极端情况，
  所以**保留但不再当作性能优化**；
- 真正要解决的是 `pickDir` 为什么会在某些位置全负分——那需要的是
  「局部无解时选最接近目标的可行方向」的逻辑（已有初版 + 绝对兜底），
  而不是靠随机冲刺；
- 后续所有改动**一律用本工具测配对差**，CI 跨 0 就不算改进。

## 16. 入侵抵抗有了专属挂机逻辑（首次）

### 之前为什么打不了

`tools/auto.js` 里 **`invade` 出现 0 次**——挂机只知道突入探索（房间图、门、交互物、
目标探索）。入侵是 Brotato 式竞技场：一个封闭场地、一波一波敌人、每波限时存活。
实测 trace：

```
{"world":"40x26 rooms=1","active":false,"inter":0,"obj":null,"note":"","px":328,"py":216}
```

`active:false`（没有“激活房间”概念）、`inter:0`（没有交互物）、`obj:null`（无目标），
于是挂机在**无目标状态下游走**，这就是入侵卡在第 6 波的真正原因，而不是某个参数没调好。

### 新增 `driveInvade()`

`G.mode === 'invade'` 时走独立分支（不碰房间/门/交互物）：

1. **瞄准最近的敌人**（入侵靠武器自动开火，只需 `Input.mx/my` 瞄准）；
2. **保持射程带**：`band [55,110]`，首领波（wave%5==0）放大到 `[70,130]`；
   太近则后撤、太远则接近、在带内则横向绕行；
3. 场上无敌人时**向场地中心漂移**，避免贴墙；
4. 威胁值 ≥1.6 时冲刺脱离；所有移动都过 `pickDir`（含 24 方向威胁场）。

### 实测（从第 9 波起，despair，rounded，×8）

| 次 | 到达波次 | 击杀 | 存活 |
|---|---|---|---|
| 1 | 10 | 11 | 12.9s |
| 2 | 10 | 12 | 10.5s |
| 3 | 10 | 22 | 12.5s |

**结论（诚实）**：击杀从 ~9 提升到 11–22，说明它真的在打；但**一波（~25s）撑不到 1/3**
就死，仍然卡在第 10 波。生存能力是下一个要解决的问题（很可能是第 9 波敌人密度 +
挂机只会「保持距离」而不会「利用场地边缘/绕大圈风筝」）。

### 入侵 A/B 的指标分辨率问题（工具坑）

用 `--kind ab --ab-kind invade` 测开关时，A/B **都到达同一波次**（6 vs 6、10 vs 10），
配对差恒为 0，指标没有分辨率。已修两处：

- 零方差时的判定不再误报「A 更好」，改为「完全无差异（指标无分辨率）」；
- 入侵 A/B 默认从**第 9 波**起跑（原来 5 波太容易，全部 6 波），提高分辨率。

但即使从第 9 波起，只要挂机稳定死在同一波，波次指标依然无分辨率——
后续入侵调优应当改用**存活秒数**（或「波内存活比例」）作为指标。

## 18. 入侵：起始波决定了「看起来卡在哪」（关键测量纠错）

加了波间商店自动化后重测，发现之前「卡在第 6 / 第 10 波」的判断**是起始波造成的错觉**：

| 起始波 | 到达波 | 存活秒 | 击杀 |
|---|---|---|---|
| 1 | 4 | 56.6 | 129 |
| 5 | 6 | 25.5 | 75 |
| 7 | 8 | 6.7 | 13 |
| 9 | 10 | 6.7~12.9 | 13~21 |

规律：**从第 N 波起跑，大约只能再推进 1–3 波**。这不是「卡在第 X 波」，
而是**绝境难度下入侵的强化曲线极其陡峭**——每过一波，敌人强度跳得比挂机成长快。

由此产生两个测量结论：

1. 之前「从第 5 波起跑 → 卡第 6 波」被误读成「第 6 波是结构性瓶颈」，其实是起点选得高；
2. 入侵模式的 A/B 若用「到达波次」比较，会因起点不同而完全失真；
   用 `survived`（波内存活秒数）才对，且**必须固定同一起始波**（现固定第 9 波做高难验证，
   或用第 1 波做「从零能走多远」的长期能力评估）。

### 真正的瓶颈：成长速度 < 难度增长

从第 1 波起跑能打 129 杀 / 56 秒到第 4 波，说明**挂机在早期是能打的**；
后面崩掉说明挂机的成长（武器等级/物品/属性升级）跟不上绝境曲线。
本轮已加入的波间自动化覆盖：

- `ivcrate`：补给箱（Enter 领取）；
- `ivlv`：升级选项按优先级挑（dmg > aspd > crit > range > hp > speed > …）；
- `ivshop`：按「武器 > 伤害类 > 生存类」优先级购买可负担的报价，然后 `ivNextWave()`
  （游戏侧的 `ivBuy` 自带武器槽/物品上限/付款校验，所以自动点击是安全的）。

但**绝对强度仍不足**：绝境第 4 波以后就崩。下一步要针对「成长」：
优先买武器等级/合成（`ivCombine` 三合一升阶）、优先经验与材料掉落。

## 19. 结论 3：入侵「武器合成」是**确定的改进**（通过 CI，且 4/4 全胜）

### 先修了一个让所有入侵 A/B 失真的 bug

`--start-wave 1` 之前**没有真正传进页面**：yargs 把 `--start-wave` 解析成
`args['start-wave']`，而驱动读的是 `args.startWave` → 永远取不到 → A/B 实际一直在
**第 9 波**起跑。于是「合成」这种成长型改动根本来不及生效，
测出来是「无显著差异（-0.6±5.5）」。

修好之后（同一起始波、同会话交错、顺序交替）：

```
A（不合成）56.3s | B（合成）61.6s
配对差 +5.3 ± 1.6     95% CI [+3.7, +6.9]      ← 不含 0
逐对：55.8→60.0, 58.5→62.2, 55.6→61.6, 55.2→62.4  （4/4 全胜）
判定：B 更好
```

**这是三档目标里第二条通过统计检验的机制性改进**（第一条是入侵模式用冲刺）。

原因：入侵的伤害主要来自「武器阶数」而不是件数，`ivCombine` 把三件同名同阶合成
+1 阶；绝境里每波敌人强度跳得快，阶数跟不上就崩。

### 实现（`driveInvadeUI` 的 ivshop 分支）

在买之前先**扫一遍武器列表做合成**（`ivCombine` 自带「同名同阶 + t<3」检查，
直接调用安全），然后再按「武器 > 伤害类 > 生存类」买可负担的报价，最后 `ivNextWave()`。
开关：`A.opts.invadeCombine`（默认开）。

原始数据：`docs/data/ab-invade-combine.txt`。

### 顺带确认：会话漂移不存在

同一会话连续跑 4 次入侵（第 1 波起）：47.8 / 49.9 / 47.2 / 48.6 秒，100~117 杀，
**高度稳定**。所以 A/B 的配对设计是可靠的——之前的问题纯粹是参数没传进去。

## 25. 结论 11（仍不显著）+ 长跑揭示的方差真相

### 先修了测量口径：入侵现在「跑到死亡」

之前固定 60–150 秒窗口，样本永远以 `alive` 结束（实测真实死亡在第 5 波 / 127 秒附近），
对后期改动没有分辨率。现在 `runInvade` 会一直跑到 `G.state === 'dead'`（或墙钟预算耗尽）。

### 长跑重测「升级：dps vs growth（收获/幸运优先）」

```
A(dps) 184.0s | B(growth) 224.8s
配对差 +40.8 ± 77.5   SEM 44.8   95% CI [-46.9, +128.6]   ← 跨 0
逐对：151.7→281.8 (+130.1), 160.8→151.2 (-9.6), 239.5→241.5 (+2.0)
击杀配对差 +97.3
```

**仍不显著**，但要注意：

- 方向和机制一致（`ivGainMat` 同时给钱+经验，`luck` 直接乘每击杀掉落）；
- 均值被**单对 +130** 拉起来，另两对几乎是平的 → 典型的「偶尔滚起来」；
- 这说明 growth 策略**有上限收益但触发不稳定**，而不是无效。

### 顺带修正天花板

长跑实测存活 **150~282 秒**（不是之前说的 127 秒定值），对应波次 5–7。
所以入侵的真实天花板是一个**很宽的区间**，本身方差极大——这也是为什么
入侵的小改动几乎都无法通过 CI：**噪声 > 效应**。

### 结论：入侵需要的是「降方差」而非「提速」

连续 8 项入侵改动里只有 4 项通过，且通过的 4 项都比未通过的**效应更大**（+1.6~5.3s vs ±2s）。
要在剩下来的改动里测出差异，必须先把方差压下来：
- 固定开局（同样的前 3 波选择序列，减少随机掉落影响）；
- 或把「每对」改成同一局存读档的 A/B（真正同源比较）。

```
A(直接清房) 288.0s | B(资源优先) 286.1s
配对差 -1.9 ± 147.1    SEM 52.0    95% CI [-103.8, +100.1]    t = -0.04
逐对符号：- + - - + + + +                     （4 正 4 负）
```

**结论：不采纳，默认保持 `exploreOrder='fight'`。**

### 这条记录真正的价值：量化了五锁测量的极限

- 单局 `gameT` 标准差 ≈ **147–208 秒**；
- 8 对时 CI 半宽 ≈ **104 秒**；
- 因此要检出「真实的 +50 秒改进」，需要 **n ≈ 35 对**（约 70 次全局长跑，数小时）；
- 这解释了为什么本轮之前所有五锁 tweak 都不显著：**不是改动无效，而是测量不够**。

1. **局部指标替代全局指标**：例如「单房间清场秒数」「每 100 秒击杀数」
   这类几百个样本/局的量，方差远小于「整局存活」；
2. 或者**固定开局种子 + 固定房间布局**，把随机性压到只剩操作差异；
3. 全局 `gameT` 只用于「是否崩坏」的粗筛，不再用于判定优劣。

## 27. 结论 13：局部指标已接入，但「击杀率」同样不稳定（符号会反转）

### 已实现的局部指标（`runFullRun` 每 250ms 采样）

| 字段 | 含义 |
|---|---|
| `roomClears` | 本局成功清场的房间数 |
| `roomClearMean` / `roomClearMax` | 清场耗时均值 / 最大值（游戏秒） |
| `killPer100` | 每 100 游戏秒的击杀数（滑动窗口） |

A/B 支持 `--metric roomClearMean|killPer100|gameT`。

### 实测：同一改动、同一指标，两次符号相反

用 `killPer100` 比较「资源优先 vs 直接清房」：

| 批次 | 窗口 | A(fight) | B(resources) | 配对差 | 95% CI | 判定 |
|---|---|---|---|---|---|---|
| 5 对 | 20 s | 8.1 | 33.4 | **+25.3 ± 27.4** | [1.3, 49.3] | B 更好（曾“通过”）|
| 6 对 | 10 s | 16.4 | 6.9 | **-9.5 ± 15.2** | [-21.7, 2.6] | 无显著差异 |

**同一改动、同一指标、只改了采样窗口和样本数，结论就翻了个面**。逐对数据还出现多个 `0` 值
（短局里 10s 窗口落空，没有击杀），说明该指标在「局短 + 死亡早」时不稳定。

### 教训（写进方法论）

1. 「局部指标方差更小」这个假设**未经证实就不能用**。清场样本实测每局只有 1–2 个，
   击杀率窗口也只有十几个，和整局 `gameT` 在同一量级上都不够；
2. 指标必须**先验证自身稳定性**：同一组配置跑两遍，看指标均值/符号是否一致，
   再拿它做 A/B；
3. 目前五锁下**没有任何指标**被证明能分辨 <50% 的差异。
   因此在拿到稳定指标之前，五锁侧的「优化」都只能是推测。

### 下一步（明确）

1. 增加**单局样本密度**：不再「一局一个数」，而是把每局的清场耗时、每 10s 击杀
   全部记录成数组落盘（`docs/data/`），做分布比较而非均值比较；
2. 用 **Wilcoxon/自助法**这类非参数检验替代均值 CI（对长尾更稳）；
3. 或者接受现实：五锁通关可能不是靠微调能达到的，需要**结构级改变**
   （例如给挂机加“集火/撤退/绕后”的状态机，而不是继续调权重）。

原始数据：`docs/data/ab-killper100-20s.txt`、`docs/data/ab-killper100-10s.txt`。

## 28. 结论 14：结构级改动（战斗状态机）也没能通过——方差彻底压过效应

### 做了什么

把原来逐帧的临时战斗判断（护甲阈值 + 距离带）换成**三态状态机**，带滞回：

| 状态 | 进入条件 | 行为 |
|---|---|---|
| `RETREAT` | 护甲破且未恢复 / 低血 | 拉远 170~250，**不开火** |
| `FOCUS` | 场上 ≤3 敌且血量健康 | 压到 40~90 抢输出 |
| `KITE` | 其它（人海） | 保持 90~150 绕行 |

带滞回窗口（0.6~0.8s）避免边界抖动；`A.opts.fightSM` 可切换回旧逻辑做 A/B。

### 6 对结果（五锁，90 秒窗）

```

配对差 -33.2 ± 136.1   95% CI [-142.1, +75.7]    ← 跨 0

```

**不显著，且方向为负**。默认改为 `fightSM: false`（未经证实的行为不设为默认）。

### 这是第三个「结构级改动也无法判定」的证据

| 尝试 | 类型 | 结果 |
|---|---|---|
| 资源优先（改目标顺序） | 结构级 | 8 对后符号对半 |
| 视距/冲刺/合成/买武器（入侵） | 机制级 | 4 条通过（效应 1.6~5.3s，成对一致） |
| 战斗状态机 | **结构级** | 6 对 CI 仍跨 0（±136s） |

规律：**入侵的改进能测出来（因为单局短、方差相对小），探索五锁的改进测不出来
（单局 200~440 秒、SD≈150）。**

### 诚实的现状与建议

- 目标①（绝境五锁通关）**在本会话的测量能力下无法通过 A/B 调优推进**；
- 要推进只有两条路：

     这样同 seed 就是同结果，A/B 方差会骤降到近 0）← 技术可行、价值最高；
  2. 放弃 A/B，用「多打几十局看能否偶然通关」的方式碰运气（不可取）。

原始数据：`docs/data/ab-fight-sm.txt`。

## 29. 结论 15：确定性模式把方差降了约一半，但**没有做到可复现**

### 实现（`core.js` 的 `TSW.det`）

游戏用真实经过时间算 dt（`game.js:693`），所以同 seed 也跑出不同结果。
`det` 模式给游戏一条**严格按 16.667ms 递增**的虚拟时间轴，每帧固定一个 tick：

```js
if (det) {
  acc += dt * Math.max(1, speed);
  while (acc >= VIRT_DT && steps < MAX_STEPS) { acc -= VIRT_DT; virt += VIRT_DT; fireTick(); steps++; }
  if (steps >= MAX_STEPS) acc = 0;
  return;
}
```

另加 `TSW.det.ticks` 计数与「按 tick 预算收尾」（默认 18000 tick = 300 游戏秒）。

### 实测（五锁，seed 7，同配置跑 3 次）

| 次 | ticks | gameT | kills | dmg | 结局 |
|---|---|---|---|---|---|
| 1 | 16333 | 260 | 47 | 2821 | death |
| 2 | 10070 | 159 | 34 | 3295 | death |
| 3 | 18037 | 297 | 36 | 2409 | timeout |

**对比非 det 模式**（同配置历史数据：gameT 200~440、SD≈150）：

- 方差**降了一半左右**（本轮 159~297，SD≈72）；
- 但**仍然不可复现**：同一 seed 三种结局，因为 `MAX_STEPS` 截断取决于机器负载，
  「哪些帧被截断」是真实时间的函数 → tick 序列仍然不同。

### 结论与取舍

- `det` 模式**值得保留**（方差减半是实打实的），已接 `--det 1`；
- 但它不是「完全可复现」，因此**仍需配对 A/B**，只是所需样本数减半；
- 要做到真正可复现，必须让**每帧恰好一个 tick 且不丢弃**
  （即 `steps` 永远 =1、`acc` 永不溢出）——这要求把倍速拆成「多帧渲染、单 tick 逻辑」，
  是一次结构性改造，超出本轮范围。

### 现状总结（目标①）

| 手段 | 状态 |
|---|---|
| 配对 A/B | 已实现，但五锁单局 SD≈70~150，需 ~35 对才能测 +50s |
| 确定性模式 | 已实现，SD 减半（≈72），仍不可复现 |
| 局部指标 | 已实现，但自身不稳定（符号会反转） |
| 结构级改动（状态机/资源优先） | 都做了，都测不出 |

## 30. 结论 16：修复两个会让**所有 A/B 结论失效**的 bug（NULL 测试的价值）

方法：跑一组「两臂完全相同」的 A/B（`optA == optB`）。正确结果是「无显著差异」。
任何偏离都说明 A/B 本身有偏置。

### bug 1：`det` tick 计数没有按局重置

`TSW.det.ticks` 是全局累计，第一局用完后第二局的「tick 预算」开局即满，
于是 A/B 里第 2 局开始 `gameT` 只有 **2~3 秒**（NULL 首测实测 `145 → 3`）。
修复：每次 `runFullRun` 记录 `detT0 = ticks`，预算用 `ticks - detT0`。

### bug 2（致命）：顺序交替时**臂标签没有换回来**

为抵消会话漂移，我把每对改成「A→B / B→A」交替，但比较时仍把「先跑的」当 A 臂。
于是**每一对翻转的符号都是错的**——真实 A/B 的结论会被系统性地反转。

NULL 测试直接暴露了它：

```
修复前（两臂完全相同！）：delta -63.0 ± 39.5   95% CI [-101.7, -24.3]   → 判定「A 更好」
逐对：(289,217,-72), (257,145,-112), (214,196,-18), (293,243,-50)
```

**两臂完全一样却「显著」判定 A 更好** —— 这就是标签错位的指纹。
修复：`const a = flip ? second : first; const b = flip ? first : second;`

```
修复后：delta +10.5 ± 82.9   95% CI [-70.7, +91.7]   → 「无显著差异」✔
逐对：(278,287,+9), (245,144,-101), (88,185,+97), (194,231,+37)
```

### 这两个 bug 意味着什么

- 本会话之前**所有**用 `--kind ab` 得出的结论（含 4 条「通过」的入侵改动）
  都可能被 bug 2 的符号反转污染——**必须重测**；
- 新增 `warmup`（首局丢弃）用来消除「首局冷启动」噪声，实测稳态三对仅差 ±3 秒；
- 现在的标准做法：**先跑 NULL 自检，通过了才采信 A/B 结果**。

## 40. 结论 25：导航兜底**从来没有生效过**（被 navigation 覆盖）+ 修复

### 诊断（`?trace=1`，classic，seed 7）

t=186 至 t=219（30+ 游戏秒）玩家坐标**固定在 (613,924)** 完全不动，
目标是 414px 外的「实验血清」，路标 `wp=[456,808]`，`note` 为空。

### 根因：兜底写在了 navigation **之前**

```js
// 旧代码（drivePlay 内，navigation 之前）
if (A._forceUntil && G.time < A._forceUntil && A._forceDir) { mx = A._forceDir[0]; my = A._forceDir[1]; }

} else if (dl > 12) { [mx, my] = pickDir(p, dx, dy); }   // ← 把兜底覆盖掉了
```

```js
if (A._forceActive) { mx = A._forceActive[0]; my = A._forceActive[1]; }
```

## 42. 结论 27：`forgeMode='any'` 是**明确的负效果**（过层率 0/5 vs 3/5）

| 配置 | 过层率（5 种子） | 备注 |

### 为什么 `any` 有害（机制解释）

`'any'` 会让挂机只要**任意已装备武器**可升级就去锻造，包括副武器（常常是低阶、
甚至评分很低的枪）。这导致：

1. 墨水被花在**弱的副武器**上（+25% × 低基数 = 几乎无收益）；
2. 挂机为锻造反复跑图，**清房时间被挤占**；
3. 主武器的升级反而被推后。

所以「钱花在武器上」这条规律要加限定：**要花在主武器（当前火力来源）上，而不是任何武器**。

### 方法层面的收获（第二次验证）

| 指标 | 能否分辨 |
|---|---|
| `gameT`（连续、SD 70–150） | 不能（本例把 0/5 vs 3/5 显示成 -9s）|
| 过层率（二元） | **能**（0/5 vs 3/5，5 种子即清楚）|

**今后一律先跑过层率，再用 gameT 看细节。**

### 机制解释

在绝境/经典里，**清房时间是硬约束**（波次/房间拖着就会被淹）。所以：

1. 任何「为了升级武器而额外跑图」的行为都在**挤占清房时间**；
2. `held` 之所以最优，是因为它**只在顺路时**（手持武器刚好能升）才去，几乎不额外绕路；
3. `main`/`any` 都会让挂机主动绕去锻造房，代价超过武器 +25% 的收益。

### 这条结论同时修正了「钱花在武器上」那条规律

入侵模式里「钱买武器」有效，是因为**商店就在波次之间、不需要跑图**（零机会成本）。
探索模式里锻造需要跑图（有高机会成本）——**同样是「钱变武器等级」，结论相反**。

**规律要加限定：只有当「把资源变成战力」的机会成本接近 0 时，这条才成立。**

### 后续方向（明确不再走的路）

不再在「锻造/买什么」上做文章。探索侧的瓶颈是**清房效率**本身，下一轮应从

## 58. 结论 42：门口等护甲的阈值与游戏真实规则**错位**；对齐后 3/12 → 5/12

### 发现的错位

`drivePlay` 在战斗房门口等护甲回满的条件是 `p.lastHit > 1`，但游戏规则是

```js

if (tgt.label === 'fight' && p.armor < p.maxArmor - 1 && p.lastHit > 1 && dl < 90)

// 新：与真实回复时机对齐（可配置 A.opts.armorWaitT，默认 3）
if (tgt.label === 'fight' && p.armor < p.maxArmor - 1 && p.lastHit > armorWaitT && dl < 90)
```

| 配置 | 过层率 | 逐对变化 |

| 基线 | 3/12 | — |

数值差异 ±2 局在 n=12 的噪声边缘（±12%），**不作统计学宣称**；
但这条改动与 §43/§53 那些「调参」不同：它修的是**与游戏规则的错位**，
在机制上不可能更差（静止等待期间护甲不会增长 = 纯浪费）。
因此**设为默认**。

### 布伦特式总结：探索侧现在有两类有效改动

## 60. 结论 44：失败局**不是「清房太慢」**，而是「早死 + 受击次数极少」

12 种子完整诊断（`docs/data/classic-fail-vs-pass.jsonl`）：

| 组 | n | 击杀 | 游戏秒 | **受击** | 清房数 | **平均清房秒** |
|---|---|---|---|---|---|---|
| 过层 | 3 | 137 | 547 | 23.7 | 6.7 | **26.3** |
| 失败 | 9 | 32 | 155 | **3.1** | 2.7 | **18.0** |

### 两个反直觉的发现

1. **失败组的清房更快**（18.0 vs 26.3 秒/房）——所以「清房效率」不是失败原因，
   此前把 `roomClearMean` 当作优化对象是**方向错误**；
2. **失败组受击次数极少**（3.1 次就死了，过层组 23.7 次才死）。

第 2 点是关键：玩家有护甲（3 次免费）+ 血量，**3 次受击就死**意味着：

- 不是被小怪磨死（那会是大量 1 点伤害）；
- 而是**单次高额伤害**或**致命机制**（爆炸、刀臂、火柱、深渊、Boss 撞击）；
- 也就是说，**挂机死于「没躲开某个致命打击」，而不是「被持续消耗」**。

### 方向修正（重要）

之前 §57 推出「清房数 → 棱镜 → 血清 → 伤害」的因果链，
但本轮数据显示失败局**在 155 秒内就死了**（来不及积累），所以：

> **第一优先级应该从「清得更快」改成「别被一击打死」**
> ——即躲闪/威胁识别，而不是 DPS 或经济。

具体要查：失败局被什么打死的（`G.hits` 的伤害来源）。这需要新的诊断字段。

原始数据：`docs/data/classic-fail-vs-pass.jsonl`。

## 61. 结论 45：watchdog 用「击杀/墨水/敌数」判卡死 → **把正常走路的局误判为卡死并强杀**

### 决定性证据（`hurtTrace` 新诊断）

给 `bench.js` 加了伤害源记录（包装 `window.hurtPlayer`，记 `dmg/pierce/mechHit/hp/armor`），
5 个种子的最后一条永远是：

```
dmg=999 pierce=1 mech=1 hp=5 armor=3
```

`dmg=999 + pierce + mech` 是 **benchmark 自己的 watchdog 强制击杀**，
不是怪物伤害。也就是说：**之前所有「失败局」其实是被测量工具杀掉的，不是被打死的。**

wolfdog 原判定签名不含玩家位置：

```js
[g.state, g.kills, g.ink, g.floor, g.endless, 存活敌人数]   // ← 没有坐标
```

挂机在**跨楼层走向下一个房间**时，30 秒内可能没有击杀、没有墨水变化、敌人数不变
→ 被判定「卡死」→ 强杀。

### 修复与效果

签名加入 `Math.round(p.x/24), Math.round(p.y/24), hp, armor`。修复后（固定 12 种子）：

| 种子 | 修复前 gameT | 修复后 gameT | 楼层 |
|---|---|---|---|
| 7 | 224 | **1044** | 0 |
| 29 | 153 | **895** | 0 |
| 31 | 500 | **865** | 0 |
| 37 | 591 | **898** | 0 |
| 5 | 271 | 519 | **1** |
| 11 | 142 | 477 | **1** |

**运行时长普遍拉长 2–7 倍**，证明这些局一直在正常活动，此前被误杀。

### 但过层率没变（3/12 vs 4/12）——暴露了第二个真问题

种子 7 存活 **1044 秒**却 `floor=0`：**挂机能连续走动 17 分钟，却一个房间都没清掉**。
所以「没进度」不是 watchdog 的错，而是**真的没有推进房间**。

→ 下一轮：把 watchdog 的进度信号改成 **`roomCleared` / 已访问房间数**，
   并诊断「为什么长时间不推进房间」。

## 62. 结论 46：**「锻造目标永不放弃」是长局零进度的真凶**（修复后 3/12 → 5/12）

### 决定性 trace（种子 7）

加了 `floorN/roomsN/clearedN` 调试字段后，t=240 → t=1200（**960 秒**）状态完全冻结：

```
t=240..1200  floor=0  rooms=11  cleared=10  obj=forge  note=''  shardN=4
```

**已经清掉 10/11 个房间，却卡在「想去锻造」上 16 分钟**，`note` 始终为空
（导航段没走到任何动作），血清数也不再增长。

原因：`pickObjective` 里锻造目标**没有放弃机制**——只要「当前武器还能升级且付得起」
就永远返回 forge，即使那个房间根本到不了（被墙隔开 / 需要钥匙 / 已经买满）。
而它是**排在战斗房之前**的，于是整个 run 被一个不可能完成的目标钉死。

### 修复

给锻造目标加放弃计时（`A.opts.forgeGiveUp`，默认 25 秒）：
连续 25 秒锁定同一个锻造房仍未完成 → `benchFor(r, 120)` 放弃 2 分钟，让 run 继续推进。

### 效果

**单点验证（种子 7，同样 1045 秒时长）**：

| | 楼层 | 清房数 | 血清 |
|---|---|---|---|
| 修复前 | 0 | **0** | 5 |
| 修复后 | **2** | **9** | **12** |

**同样时长，从「清 0 房」变成「清 9 房、过 2 层」**——这正是 §57 里成功局的形态。

**12 种子全量（每局上限 420 秒）**：

| 配置 | 过层率 | 变化 |
|---|---|---|
| 基线（旧默认）| 4/12 | — |
| watchdog 修复后（无 forge 放弃）| 3/12 | 种子 1、3、11 仍未过 |
| **+ forge 放弃（本条）** | **5/12** | 种子 1、3、11 转为过层，**无种子退步** |

### 这与本轮前面的发现是同一条因果链

1. watchdog 用「击杀/墨水/敌数」判卡死 → 正常走路被误杀（§61）；
2. 修好 watchdog 后，run 能活很久，于是**暴露出真正卡死的地方**：锻造目标永不放弃；
3. 修好锻造放弃后，长局才真正变成「清房 → 拿血清 → 过层」。

**教训：测量工具的假象会掩盖真正的 bug。** 修好 watchdog 之后才看得见 forge 死锁。

## 63. 结论 47：通用目标放弃（任何目标卡 40 秒就弃）——过层率未提升，但**最深层数创新高**

### 实现

`pickObjective` 返回的目标若被**连续选中超过 `goalGiveUp`（默认 40 秒）仍未完成**，
就 `benchFor(目标, 90)` 放弃 90 秒并立即重选。这是 forge 专用放弃了之后的**通用安全网**，
覆盖 shrine / treasure / camp / boss / 各种特殊房。

### 12 种子实测

| 配置 | 过层率 | 最深层 |
|---|---|---|
| forge 专用放弃 | **5/12** | 第 2 层（floor 1）|
| **+ 通用放弃** | 4/12 | **第 3 层（floor 2）×3** |

- 过层率：4/12 vs 5/12，**差异 ±1 局，在噪声内，不作改善宣称**；
- **但最深层数从「仅第 2 层」提升到「3 局到达第 3 层」**（seed 3 / 23 / 37，
  其中 seed 3 跑出 **1389 秒 / 286 杀**）。

### 另一个观察：个别局变得极长

seed 31 跑 **1944 秒**（仅 10 杀）、seed 19 跑 **1917 秒**（41 杀）——
这类局在长时间内低产。可能是目标放弃导致的**重选抖动**（弃 90 秒后重选到同一目标又弃）。

**因此本条保留为默认，但标记为「待优化」**：`goalGiveUp=40` 可能偏激进，
值得再测 60/90 秒两档，或给同一目标加「弃置次数上限」。

### 探索侧已验证清单（累计，固定 12 种子）

| 改动 | 过层率 | 最深层 | 判定 |
|---|---|---|---|
| 旧基线 | 4/12 | 第 2 层 | — |
| watchdog 修复 | 3/12 | 第 2 层 | 修正测量假象（必需）|
| + forge 专用放弃 | **5/12** | 第 2 层 | ✔ 有效 |
| + 通用目标放弃 | 4/12 | **第 3 层** | 噪声内，保留待调 |

**注意**：过层率（floor≥1）与最深层是两个不同指标。前者衡量「能否起步」，
后者衡量「能走多远」。通用放弃牺牲一点起步率，换来了更深的推进。

## 66. 结论 50：贴墙罚分必须**有方向性**，否则会把机器人钉在墙边

### 事故（本轮引入、当场被发现）

第一版实现把「距离墙/门/坑 < `wallMargin` 就扣 2.5 分」逐方向评估目的地。但当机器人
**本来就贴着墙**时，24 个候选方向里除了「正对外侧」的那一个，其余全部命中探测点，
于是分数被整体压低、彼此差异消失 → `pickDir` 退化成噪声。

trace 抓到的指纹很典型（seed 1）：

```
t=237..258  obj=boss  cleared=10/11  px=1029..1060  py=1165（完全不动）
```

**已经清掉 10 个房间，却在一个固定 y 上左右横摆 20+ 秒**。该 seed 原本能活 738 秒，
崩到 **30 秒**。

### 修复：只在「更靠近墙」时罚分

```js
const nearNow  = tooCloseToWallOrPit(p.x,                p.y,                p.r, margin);
const nearNext = tooCloseToWallOrPit(p.x + dx * margin,  p.y + dy * margin,  p.r, margin);
if (nearNext && !nearNow) s -= 2.5;      // 拒绝进入贴墙带
else if (nearNext && nearNow) s -= .6;   // 已经在带内：只轻微倾向别再滑墙
```

### 修复后实测（固定 12 种子，classic，goal-depth 2）

| 指标 | 上一轮基线 | 贴墙罚分（绝对式，坏） | **修复后（方向式）** |
|---|---|---|---|
| 过层率 | 9/12（75%）| 6/12（50%）| **8/12（67%）** |
| 最深层 | 第 3 层 | 第 2 层 | **第 4 层** ← 本会话最深 |

- 过层率 8/12 与基线 9/12 相差 1 局，**在噪声内**，不作改善宣称；
- 但**最深层从第 3 层提升到第 4 层**（seed 5），且 seed 1/7/11/23 都到第 3 层；
- `seed 1` 从 30 秒恢复到 **1362 秒 / 160 杀**。

### 教训（已进 AGENTS 思维）

**给「位置」打分时，必须比较「现在 vs 下一步」，不能只评估下一步本身。**
只看绝对状态的罚项会在「已经处于坏状态」时把所有选项压成一样平，
产生原地横摆这种看似有动作、实则零进度的行为。

## 67. 结论 51：把 boss 封印（seal）当**导航目标**——过层率 67% → 92%

### 根因

boss 房间在拿到钥匙之前是锁着的（`WORLD.bossLocked`）。开锁要站在封印交互物旁按 E
（`game.js:366-367`）。挂机的**交互**里确实有这一条：

```js
if (it.kind === 'seal' && G.hasKey) { tap('KeyE'); break; }   // 但只在 24px 内才执行
```

可是**目标选择从不把 seal 列为目的地**，只列 `prism` / `key`。于是挂机走到 boss 房门口，
门是锁的、又没有到封印旁，就只能在门口徘徊：trace 里 seed 19 表现为
`obj=boss`、`cleared=10/11`、坐标在 10×8 像素的小盒子里反复抖动。

### 修复

在 `pickObjective` 里，当 `WORLD.bossLocked` 且持有钥匙时，把 seal 作为目标：

```js
if (it.kind !== 'seal') continue;
if (!WORLD.bossLocked) continue;
if (G.hasKey && ...) return { pt: [it.x, it.y], label: 'seal', room: ... };
```

开关 `A.opts.openSeals`（默认开）。

### 实测（固定 12 种子，classic，goal-depth 2）

| 指标 | 上一轮 | **本轮（seal 修复）** |
|---|---|---|
| 过层率 | 8/12（67%）| **11/12（92%）** |
| 最深层 | 第 4 层 | 第 4 层 |
| seed 19 | 0 层 / 6 杀 | **第 3 层 / 252 杀** |
| seed 31 | — | 0 层（唯一失败，2060 秒仅 13 杀）|

**11/12 过第 1 层**是这条线以来的最高值。唯一的失败 seed 31 是「活得久但杀不动」
（2060 秒 / 13 杀），属于输出不足，而不是卡死。

### 累计（探索侧，固定 12 种子）

| 阶段 | 过层率 | 最深层 |
|---|---|---|
| 最初基线 | 4/12（33%）| 第 2 层 |
| 目标放弃 90s | 9/12（75%）| 第 3 层 |
| 贴墙罚分（方向式）| 8/12（67%）| **第 4 层** |
| **+ boss 封印目标** | **11/12（92%）** | 第 4 层 |

### 教训

**「能交互」不等于「会去交互」**：交互分支写了（`tap('KeyE')`），但没进目标列表，
于是永远只在顺路时才可能触发。凡是解锁进度的关键物件，都必须同时出现在
*目标选择* 和 *交互执行* 两处。

## 68. 结论 52：传送门也必须进目标列表，但**必须门控在清房之后**

### 根因（与 §67 的 seal 完全同类）

传送门是**唯一**的换层手段，无尽传送门只在最后一层（第 5 层）通关后出现
（`game.js:243`、`FLOORS` 共 5 层）。挂机对 portal 有完整交互逻辑：

```js
if (it.endless && A.opts.preferEndless ...) { note='→ 无尽'; tap('KeyE'); }
if (!it.endless && !G.endless ...)        { note='→ 下一层'; tap('KeyE'); }
```

但 `pickObjective` **从未把 portal 列为目的地**——和 seal 一模一样的缺陷：
写得再全，只要不在目标列表里，就只有在顺路时才会触发。

### 第一版（无门控）是错的

把 portal 直接放进目标列表后，它排在 boss / fight **之前**，于是传送门一出现就走，
**本层没清完就跳层**，牺牲了棱镜与血清：

| 配置 | 过层率 | 最深层 |
|---|---|---|
| 无 portal 目标（§67 后）| 11/12（92%）| 第 4 层 |
| portal（无门控）| **9/12（75%）** | **第 2 层** ← 明显退步 |

### 修复：只有本层没有未清战斗房时才走传送门

```js
const floorHasWork = rooms.some((r) => r.type === 'combat' && !r.cleared && !unreachable(r));
if (!floorHasWork) for (const it of G.inter) { ... portal ... }
```

### 实测（固定 12 种子，classic）

| 配置 | 过层率 | 最深层 |
|---|---|---|
| 无 portal 目标 | 11/12（92%）| 第 4 层 |
| portal 无门控 | 9/12（75%）| 第 2 层 |
| **portal 门控** | **10/12（83%）** | **第 4 层** |

10 vs 11 相差 1 局，在噪声内；关键是**最深层回到第 4 层**，
且击杀数明显更高（seed 5 单局 **362 杀**，之前最多 303）。

### 累计（探索侧，固定 12 种子，同种子可比）

**关键物件要同时进「目标列表」和「交互分支」；而目标列表里的顺序，
必须服从「先清完本层再离开」这条纪律，否则会以牺牲成长换取速度。**

## 69. 结论 53：已激活但没打完的房间会变成**永久孤儿**，过层率 83% → 92%

### 根因（诊断字段 `openRooms` 抓出来的）

给调试镜像加了 `openRooms`（列出所有未清房间及其类型，`*` 表示 `active`），
跑几局就看出规律：

```
"combat,boss*"              出现 49 次   ← boss 房已激活但没清
"combat,combat,boss*"       出现 24 次
"combat,combat*,boss"       出现 23 次
```

而 `cleared=12/13` 能持续 900 游戏秒不动。

代码原因：普通战斗房的目标条件是 `!r.cleared && !r.active`
（跳过已激活的，避免重复触发），而 boss 分支只看 `!r.cleared`。
于是**「走进去 → 激活 → 没打完就离开」的房间，两个分支都不再认领**，
它永远留在 `openRooms` 里，本层就永远清不完、传送门永远不出现。

### 修复

在 boss 分支和普通战斗分支之间加一个「孤儿房回收」：

```js
for (const r of rooms) {
  if (r.cleared || !r.active || unreachable(r)) continue;
  if (r.type !== 'combat' && r.type !== 'boss') continue;
  // 取最近的一个，回去打完
}
```

### 实测（固定 12 种子，classic，goal-depth 2）

| 配置 | 过层率 | 最深层 | 单局最高击杀 |
|---|---|---|---|
| 门控传送门（上轮）| 10/12（83%）| 第 4 层 | 362 |
| **+ 孤儿房回收** | **11/12（92%）** | 第 4 层 | **852** |

**852 杀**（seed 19）是这条线以来的最高单局输出，说明它能持续作战而不是早早卡住。

### 累计（探索侧，固定 12 种子）

| 阶段 | 过层率 | 最深层 | 单局最高击杀 |
|---|---|---|---|
| 最初基线 | 4/12（33%）| 第 2 层 | 196 |
| 目标放弃 90s | 9/12（75%）| 第 3 层 | 286 |
| 贴墙罚分（方向式）| 8/12（67%）| 第 4 层 | 256 |
| boss 封印目标 | 11/12（92%）| 第 4 层 | 391 |
| 门控传送门 | 10/12（83%）| 第 4 层 | 362 |
| **孤儿房回收** | **11/12（92%）** | 第 4 层 | **852** |

### 教训

**「有归属」和「能被认领」是两件事。** `!active` 这种过滤条件用来避免重复触发，
但它同时把「中途放弃的房间」变成了没有任何分支负责的对象。
凡是「状态机里只前进不回退」的目标选择，都要留一个回收分支。

## 70. 结论 54：把「追击漏网之敌」限制在房间内——**实测退步，已回退**

### 假设（看起来很有道理）

`hunt` 用 `nearestEnemy(p, 2000, false)` 找目标，**没有房间过滤**。trace 里出现过
`obj=hunt` 与 `openRooms=boss*` 同时存在数百 tick，于是推测：
它在追一个已经跑出房间的漏网敌人，房间因此清不掉。

### 改动

把追猎目标限制在当前激活房间的包围盒内；若房内没敌人，就回房间中心。

### 实测（固定 12 种子）：退步

| 配置 | 过层率 | 最深层 |
|---|---|---|
| 孤儿房回收（上轮）| **11/12（92%）** | 第 4 层 |
| + 追猎限房 | **9/12（75%）** | 第 4 层 |

**退步 2 局，已回退。**

### 为什么假设不成立

房间激活时门是关的（`setDoors(r, true)`），敌人**本来就出不去**。
所以「敌人跑到房外」这个前提是错的；而「没敌人在包围盒内 → 回房间中心」
反而让挂机在房间边缘战斗时掉头往回走，浪费了输出时间。

### 观察到的副作用

`seed 3` 击杀升到 **422**（此前 391），`seed 19` 到第 3 层 254 杀——
说明改动对**个别局**有正面影响，但整体过层率下降。
这正是「单局不可信」的又一个例证。

### 结论

这条留在文档里作为**被数据否掉的假设**：
`obj=hunt` 与 `openRooms=boss*` 共现**不等于**因果关系——boss 房处于 active
但无人清，是 §69 孤儿房问题，与 hunt 的目标选择无关。

## 71. 结论 55：**所有 12 局结束时都留着未清的 boss 房**——这才是进不了无尽的结构性原因

### 方法改变：统计替代推测

前两轮用 trace 推测因果，一次对一次错。本轮给结果行加了两个字段：
- `endFloor`（结束时所在楼层）
- `openRoomsAtEnd`（结束时仍未清的房间列表，`*` 表示 `active`）

跑固定 12 种子后直接分类统计：

|---|---|

| 含 boss（已激活未清）| 2 |

**12 局里没有一局清完本层** → 传送门（尤其是无尽传送门）**永远不出现**。

### 目标优先级：boss 被 prism 抢了

统计 `obj` 与 `openRooms` 的共现，最高频组合是：

```
openRooms=boss   obj=prism       31 次
```

boss 房**已经解锁**，但挂机跑去捡棱镜而不去打 boss —— 因为 `prism` 分支排在 `boss` 之前。

### 修复

当「boss 房是本层唯一未清的」时，把 boss 提到 prism 之前：

```js
const onlyBossLeft = boss && !boss.cleared && !boss.active
  && (!WORLD.bossLocked || G.hasKey) && !unreachable(boss)
  && !rooms.some(r => r.type === 'combat' && !r.cleared && !unreachable(r));
if (onlyBossLeft) return { ..., label: 'boss', room: boss };
```

实测（固定 12 种子）：

| 指标 | 修复前 | 修复后 |

| 过层率 | 8/12（67%）| **10/12（83%）** |
| 最深层 | 第 4 层 | 第 4 层 |
| 单局最高击杀 | 382 | **408** |

### 但「清完本层」仍然是 0/12 —— 问题比调度更深

即使修好优先级，`openRoomsAtEnd` 仍然普遍剩 **4–7 个 combat 房**：

```

seed 19: combat,combat,combat*,combat,combat,boss            (6 个)
```

每层房间数是 **11 → 13**（`world.js` 随楼层增加），而挂机的清房速度没有相应提高。
所以真正的瓶颈是**单位时间清房数**，不是目标选择。

转向「清房效率」：
1. 用 `roomClearMean` 比较过层局与失败局的实际清房耗时；
2. 测试「房内贴身清怪」类改动（提高命中率、缩短击杀时间）；
3. 目标从「调度正确」转向「每层能在死亡前清完」。

## 73. 结论 57：清房慢**不是**命中率/被围殴问题，而是游戏自身的波次节奏

### 拿到了真实战斗数据（修好诊断打点后）

上一轮 `fightD` 全是 `-1`，原因是两个：
1. 打点在导航段，那里 `G.enemies` 已按 `spawnT`/`deathFightLeft` 过滤为空；
2. 累积窗口与 trace 时机同步，采到的总是刚重置的值。

修法：把累积移到 `drivePlay` **末尾**、`A.dbg` 之前，用固定 30-tick 窗口。

### 数据（seed 5，239 个战斗样本）

**战斗距离分布**：

| 距离 | 占比 |
|---|---|
| < 40px | 1% |
| 40–90 | 8% |
| **90–150** | **88%** |
| 150–250 | 3% |

均值 131px，中位 148px —— 挂机**几乎总是在 90–150px 交火**（正是 `KITE` 射程带）。

**场上敌人数（`fightN`，38 个样本）**：

| 数量 | 占比 |
|---|---|
| **1–3 个** | **97%** |
| 4–8 个 | 3% |

均值 **1.5 个**，中位 **1**，峰值 6。

### 两个假设被同时否定

1. **不是命中率问题**：武器有效射程（`spd × life`）是
   `nail 255px`、`hail 228px`、`rivet 344px`、`twin 252px` —— 交火距离 90–150px
   **稳稳落在射程内**；
2. **不是被围殴**：97% 的时间里场上只有 1–3 个敌人。

### 真正的原因：波次节奏

`game.js:229`：

```js
if (rm.waveT <= 0 && !G.enemies.some(e => !e.dead && e.room === rm)) { spawnWave(rm) ... }
```

**下一波必须等当前波全部死光，再加 `waveT = .5 + list.length * .07` 秒延迟。**
所以一层的清房时间 ≈ Σ(各波间隔 + 杀光当前波的时间)，
**挂机唯一能压缩的是「杀光当前波」这一项**，而它已经在最优射程内作战。

### 结论与方向修正

「提高命中率/贴近敌人」这类改动**没有空间**（数据已排除）。
要缩短清房时间，只有两条路：
1. **提高单体 DPS**（血清/武器等级）——回到 §57 的因果链；
2. **减少无谓走位**（等下一波时别乱跑），但这只在波间生效，量级很小。

因此探索侧的下一个杠杆是 **DPS 本身**，而不是走位或射程。

## 74. 结论 58：武器等级一直是 0 —— 因为锻造目标瞄的是**房间中心**而不是**铁砧**

### 发现（本轮最关键的 bug）

新增两个结果字段后立刻暴露：

```
seed 5:  dps=136  wlv={}      ← 武器等级为空
seed 31: dps=66   wlv={}      ← 同上
```

**所有局的武器等级都是 0**。而 `obj` 统计显示 `forge` 只被选为 4 次
（对比 `fight` 47 次、`portal` 15 次），墨水却稳定涨到 **200–247**（首级只要 45）。

两个独立缺陷叠加：

1. **顺序**：forge 分支排在战斗房之后，`forgeMode='held'` 只在「顺路」时才回去；
2. **瞄准点（致命）**：forge 目标返回的是**房间中心** `(cx*16+8, cy*16+8)`，
   而 E 提示只在**铁砧交互物 24px 内**出现（`game.js:394`）。
   走到房间中心 ≠ 站到铁砧旁，所以**从来没按到过 E**。

### 修复

1. `A.opts.forgeFirst`（默认开）：墨水够升级且武器未满级时，锻造排在战斗房**之前**；
2. 目标点改为**铁砧本身**：

```js
const bench = (G.inter || []).find(i => i.kind === 'forge' && !i.used && roomAt(i.x,i.y) === r);
const tgt2 = bench ? [bench.x, bench.y] : [r.cx*16+8, r.cy*16+8];
```

### 实测

**单局验证（seed 5，同样配置）**：

|---|---|---|---|---|
| 修复前 | 1 | 49 | `{}` | 60 |
| **修复后** | **3** | **378** | **`{shuriken:3, nail:3}`** | **292** |

**DPS 7.7 倍、击杀 4.9 倍、武器满级（3 级）**。

**12 种子全量**：

|---|---|---|
| 过层率 | 10/12（83%）| **11/12（92%）** |
| 最深层 | 第 4 层 | 第 3 层 |

过层率 +1 局（噪声内），**最深层反而降 1**，但 **DPS 中位数翻 2–3 倍**是实质进步。

### 为什么 DPS 涨幅不如单局那么夸张

只有 **seed 5** 到了 378（双武器满级）；多数局在 112–155。
说明**不是每局都能碰到锻造房、或攒够墨水走到它**——
本层有没有 forge 房是随机的（`SPECIALS` 里 forge 只是其中一种）。

### 下一步

## 75. 结论 59：锻造修复有效，但**锻造房本身就是稀缺随机事件**（约 44% 的楼层没有）

### 量化（5 种子，逐局统计「遇到几个锻造房」vs「完成几次升级」）

| 种子 | 最深层 | 遇到锻造房 | 完成升级 | 最终 DPS |
|---|---|---|---|---|
| 1 | 第 2 层 | **1** | **3** | 102 |
| 11 | 第 4 层 | **1** | **3** | 133 |
| 3 | 第 1 层 | 0 | 0 | 89 |
| 5 | 第 2 层 | 0 | 0 | 89 |
| 7 | 第 2 层 | 0 | 0 | 78 |

- **凡遇到锻造房的局，都成功升满 3 级**（DPS 102–133）；
- **没遇到的局 DPS 只有 78–89**。

楼层覆盖率实测：trace 采样中 `forgeRooms=1` 有 65 帧、`forgeRooms=0` 有 51 帧
→ **约 56% 的楼层带锻造房，44% 没有**。

### 结论

§74 的修复（瞄准铁砧）**确实解决了「遇到也升不了」的问题**；
剩下的是**机会问题**：挂机通常只到 1–3 层，遇上锻造房的概率有限。
这也解释了为什么中位 DPS 只有 112–155，而个别局能到 378（两层都碰到锻造房）。

### 另一条路也被排除

查了军械库（`arsenal.js`）：它只**放出一把武器**（`G.inter.push({kind:'weapon'})`），
**不提升等级**。所以武器升级在探索里**只有锻造房一条路**，
不存在「第二升级通道」。

### 因此下一步不是继续修锻造，而是「让锻造房出现得更有用」

三个可行方向（按预期收益排序）：
1. **清更多房间**——锻造房只有清到才会遇到，而挂机常只清 5–7 个；
   → 本质仍是 DPS 循环，回到「先有伤害才能清更多房」的死结；
2. **提高遭遇概率**：优先走向未探索的特殊房（`SPECIALS` 含 forge）；
3. **降低对锻造的依赖**：用血清/武器数量替代等级（如 `weaponPick` 更激进地换更强的枪）。

## 76. 结论 60：特殊房优先 —— 遭遇率提升有限，**楼层随机性是硬约束**

### 改动

原来特殊房（`treasure/shop/camp/dialysis/barracks`）排在战斗房之后，且
`trial/idol/vault/forge/shrine/arsenal` **完全没被当作目标**。
新增 `SPECIAL_ROOM_TYPES`（11 种）与 `specialsFirst`（默认开），在战斗房之前探访。

### 实测（固定 12 种子，classic）

| 指标 | 上轮（§75）| **本轮** |
|---|---|---|
| 过层率 | 11/12（92%）| 10/12（83%） |
| 最深层 | 第 3 层 | 第 3 层 |
| **遇到锻造房** | 2/5 局 | **4/12 局** |
| 完成升级 | 2/5 局 | **5/12 局** |
| 最高 DPS | 155 | **209**（seed 5）|
| 最高击杀 | 291 | **322**（seed 17）|

### 解读

- **有效的一面**：升级局数、DPS 上限、击杀上限都提高了；
  `seed 5` 单局 DPS 209、`seed 11` 遇到 **2 个**锻造房并升满 3 级；
- **无效的一面**：过层率 10 vs 11（噪声内），且**仍有 8/12 的局一次锻造房都没遇到**。

### 硬约束：锻造房是楼层生成的随机事件

楼层有 56% 概率带锻造房，而挂机通常只推进 1–3 层。
即使特殊房优先，**也改变不了「这层根本没有锻造房」**。
所以靠「多探访」提升 DPS 的天花板已经到顶。

### 结论与下一步

特殊房优先**保留**（无害且有正向指标），但它不是突破口。
真正要解决的是 **DPS 的第二来源**。查过军械库（只给武器不给等级）、
商店（卖武器/血清，不升级）。

下一步可测的两条（都不依赖锻造房）：
1. **血清取舍**：当前 `scoreShard` 用固定权重表，可以按「对当前武器的实际增益」重算；
2. **武器替换**：`weaponPick` 现在比较 `wScore`（偏好表），改为比较**真实 DPS**
   （`dmg × rate × n × (1+.25·lv)`），让它在捡到更强的枪时果断换掉弱的。

## 77. 结论 61：按「真实 DPS」替换武器**会减少武器数量**，反而不利于总输出

### 动机

`weaponPick` 原来比较 `wScore()`（偏好表分数），不看实际伤害。
改成比较真实 DPS `dmg × rate × n × (1+.25·lv)` 后，理论上应该总能选到更强的枪。

### 实测（单局对照，同 seed）

| seed | 配置 | 最深层 | DPS | 武器 | 击杀 |
|---|---|---|---|---|---|
| 5 | OFF（偏好表）| 第 2 层 | 120 | **['nail','twin']** | 151 |
| 5 | **ON（真实 DPS）** | 第 2 层 | **79** | **['nail']** | **251** |
| 13 | OFF | 第 3 层 | 142 | ['nail','helix'] | 158 |
| 13 | ON | — | — | — | — |

### 反直觉但合理

开启后 `seed 5` **只剩一把武器**，DPS 从 120 掉到 79，**但击杀从 151 涨到 251**。

原因：`wCap()` 允许携带**多把武器**，而多把武器**同时开火**是叠加输出。
「按 DPS 替换」的判据是 `nw > cur + .5`——它让挂机**用强枪换掉弱枪**，
但在「容量未满」时这没有意义（`p.weapons.length < wCap()` 本来就会拿），
反而在某些分支上把已有的弱枪挤掉，**净结果是武器数变少**。

### 结论

`weaponDps` **不设为默认**（保持 OFF）。这条改动留在代码里作为可选开关，
并记入「被数据否掉的假设」——**单看 DPS 数字不够，武器「数量 × 同时开火」才是总输出**。

### 下一步方向修正

既然「多持武器」比「单把强枪」更有效，而武器来源是：
- 地上的 `weapon` 掉落；
- 军械库（`arsrack`，选一把）；
- 商店（卖武器）；

那么真正该优化的是 **`wCap` 是什么、以及怎么更快填满它**。
下一轮先查 `wCap()` 的实际值与提升条件。

## 78. 结论 62：`wCap()` 只有 **2**，而「按 DPS 换枪」会把它换回 1 把 —— 已修

### 关键机制

`shards2.js:93`：`const wCap = () => (G.S && G.S.lone ? 1 : 2);`

**最多只能同时携带 2 把武器**（`lone` 诅咒时为 1）。而游戏里多把武器是
**同时开火**的，所以「2 把弱枪」的总输出常常高于「1 把强枪」。

### 原来的缺陷

地面武器掉落的判定是 `nw > cur + .5 || p.weapons.length < wCap()`：

- 容量未满 → 直接拿（正确）；
- **容量已满（2/2）→ 只要新枪「更强」就按 E**，
  而游戏此时是**替换手持的那把**，于是武器数**停在 2 但换掉了正在开火的一把**，
  某些路径下还会掉回 1 把。

实测证据（seed 5，开启 `weaponDps` 后）：

| 配置 | 武器 | DPS | 击杀 |
|---|---|---|---|
| 偏好表（OFF）| `['nail','twin']` | 120 | 151 |
| 真实 DPS（ON，旧逻辑）| **`['nail']`** | **79** | 251 |

**武器数从 2 掉到 1，DPS 反而更低。**

### 修复

容量已满时**不再仅凭「更强」换枪**：

```js
const atCap = p.weapons.length >= wCap();
const worthSwap = A.opts.weaponSwapAtCap ? (nw > cur * 1.35) : !atCap;
if (worthSwap || p.weapons.length < wCap()) { ...拿... }
```

即默认**满容量时不换**（保留两把同时开火），只有显式开启 `weaponSwapAtCap`
且新枪强 35% 以上才换。

修复后（seed 5）：`['nail','shuriken']`、**DPS 176**（此前 79）。

### 结论

- `weaponDps` 仍默认 **OFF**（偏好表与实际强度相关性不差）；
- **满容量不换枪**成为默认行为——这条是净收益，因为它保住了「双持同时开火」；
- 下一步应关注**怎么更快填满 2 格**（掉落 + 军械库 + 商店），而不是换更强的枪。

## 79. 结论 63：按「奖励房优先 + 清完本层」重排目标，并引入进度决定型评分

### 房间优先级（按需求实现）

```
奖励房（宝箱/商店/军械库/保险柜/营地/锻造台/透析/兵营/神龛/试炼/偶像） ← 最优先
   ↓
无伤害房（点权 1）／有机关无刷怪房（点权 2）／未打过（点权 3）
   ↓
boss（4，需先开封印）
   ↓
过层传送门
```

- **每层必须清完才走**（除非强化吃满 / 无尽终局）；
- 拿到实验血清后可直接下一层；
- **有实验血清副作用时必须在本层靠「打没打过的房间」消耗掉**，不许带到下一层
  （`G.exp.left` 是剩余场次，每打完一场递减）。

### 强化物先于刷怪房

武器 / 技能芯片 / 棱镜 / 实验血清在**视线可达且确实能拿**时排在战斗房之前
（`powerupFirst`，默认开）。踩过的坑：第一版不看「能不能拿」，
导致同一把地上武器被反复当目标追了 193 个采样帧 —— 现在要求
「容量有空位」或「比手上的强」、「尚未有技能」才追。

### 评分（进度决定性）

```
penalty = Σ (3.0 × Δhp² + 1.0 × Δarmor²) × dt     // 平方，血量权重 > 护盾
score   = maxFloor × 100000 − penalty             // 进度是决定性项
```

实测三局（classic）：`maxFloor` 1–2 → score 约 10 万–20 万，penalty 33–111。
进度项比惩罚项大 3 个数量级，**符合「进度为决定性评判标准」**。

### 已确认但尚未实现的机制（下一轮）

- **格挡 / 弹反**：近战武器挥击会调用 `deflectBullets`，
  **销毁命中子弹**并有 35%（或武器 `refl`）概率**反弹伤害（8×dmg）**
  —— 面对弹幕时主动挥击 = 攻防一体，值得专门利用；
- **boss 招式躲避**：目前会迎向激光扫射，需要按招式类型（扫射/锥形/追踪）分类处理。

## 80. 结论 64：boss 激光扫射此前**完全没有建模**；近战格挡需要主动挥击

### 激光的真实机制（`boss.js:634`）

```js
const r0 = L2.r0 || 0;
segDist(p.x, p.y, owner.x + cos(a)*r0, owner.y + sin(a)*r0, ex, ey) < L2.w/2 + p.r - 2
L2.a += L2.va * dt          // 光束自己在转
```

- 光束是**从半径 r0（多为 46）到 len（420~460）的一条线段**，`a` 随时间以 `va` 旋转；
- **r0 以内完全无伤害**（贴脸是安全的）；
- r0 到 len 之间致命，且**会扫过来**。

**挂机此前对 `G.lasers` 的引用数是 0** —— 它根本不知道激光存在，
所以会一边躲别的弹幕一边走进扫射带，这就是「迎向激光」的成因。

### 修复

1. `spotDanger` 里建模激光：算到光束轴的**弧长距离**，并对 `.35s` 后的位置做预测；
2. 新增 `laserPush()` 返回**逆向扫射**的切向推力 + 就近内缩/外撤的径向推力，
   在战斗移动前叠加，`A.status.note = '躲激光扫射'`。

### 近战格挡（`weapons.js:209`）

近战挥击会自动 `deflectBullets(...)`：**销毁命中的子弹**，并有 35%
（或武器 `refl` 值）概率**反弹造成 8×dmg**。

但原来的开火条件是 `wantFire = !!neF && ...`（要求有视线内敌人），
所以**弹幕飞来但附近没目标时不会挥击 → 不会格挡**。
已加：近战且在 96px 内有子弹朝自己飞来时，无论如何挥击（`meleeBlock`，默认开）。

### 测量结果：**无法判定**（如实记录）

AB（`rounds 3`，`seconds 90`，metric `score`）：

```
A(格挡关) 66657.2 | B(格挡开) 33313.5
配对差 -33343.7 ± 57724.3   95% CI [-98664.9, +31977.5]   ← 跨 0
逐对：(99979.6, 99942.4) (99996, -2) (-4, 0)
```

逐对差异在 0 与 10 万之间跳变 —— **短时长下多数局到不了 1 层，分数只有 0 或 10 万两个值**，
配对差没有分辨率。**因此不作任何效果宣称**，两项改动按「机制正确、无害」保留。

### 顺带修掉的测量 bug

`scripts/headless-bench.mjs` 的 AB 硬超时是 `rounds × 2 × perRun + 150`，
**漏掉了 warmup 的那一对**（实际要跑 `rounds*2 + 2` 次），
导致每次 AB 都会在硬超时被杀。已改为 `(rounds * 2 + 2) * perRun`。

## 81. 结论 65：近战槽位不参与换弹换枪；后期武器按「单发伤害」加权

### 近战 + 远程 混搭时不换枪（需求已验证）

`weapons.js` 的 `usesAmmo(w)` 对近战返回 false，但换弹窗口的守卫只检查了
「两把都有弹药」——**主手近战、副手远程**时，远程（有弹匣）作为副手仍会被切进来，
把近战挤掉，连带丢掉格挡能力。

实测（`brawler` 流派，seed 5）：换枪日志里出现
`换弹切副武器 nail` / `切回主武器 nail` 共 22 次，而 `nail` 是有弹药的副手。

修复：只要**任一槽位是近战**（8 种 kind：melee/thrust/spin/whip/slam/iai/fist/reap），
就不进入换枪逻辑。逻辑表验证：

| 槽位组合 | anyMelee | 是否换枪 |
|---|---|---|
| melee + gun | true | **否** |
| gun + reap | true | **否** |
| gun + gun | false | 是（正确）|
| melee + reap | true | **否** |

### 后期武器权重（`weaponLateBias`，默认 90）

每级升级乘在**基础伤害**上，所以「单发高」的武器（`hammer` 26、`longshot` 36、
`cluster` 20）后期成长优于射速型（`nail` 7、`hail` 3）。
当手头墨水 ≥ `weaponLateBias`（默认 90，够锻造两次）时，按
`min(2.5, 单发/24)` 追加权重。墨水不足时不生效，避免前期偏好「重而慢」的枪。

### 五锁绝境当前基线（本轮实测，全部 5 修饰符生效）

**过层 2/5，最深第 2 层**，`modifiersAtEnd` 确认五个修饰符全部在生效。

## 82. 结论 66：α 血清零容忍 + 满血过层门槛；五锁过层率未变但输出上升

1. **α 血清零容忍**：α 生效期间（`G.exp.id==='a' && left>0`）任何一次受伤都扣**血量上限**

   或商店卖心时，先回血再走传送门。**这条会覆盖 `fount` 的关闭默认值** ——
   因为「每层满血进入」是更硬的需求，而治疗泉只在需要时才用。

## 83. 结论 67：满血门槛曾把整局钉在治疗泉上（700 秒零进度）

### 用 trace 定位「击杀很高却过不了层」的失败局

`seed 31`（五锁）trace（字段提取自 `DBG` 行，见下方解析坑）：

```
t=540 .. t=1260   clr=7/11   obj=''       ink=23   ← 整整 720 秒零进展
t=1260 .. 结束     clr=8/11   obj=fount    ink=24   ← 卡在治疗泉
```

### 两个真 bug

1. **治疗泉只回 2 点血且一次性**（`game.js:378` `healPlayer(2); it.used = true`）。
   我的 `fullHpGate` 假设它能回满，于是差 1 点血也会去，结果**永远补不满**。
   修复：仅当 `p.hp + 2 >= p.maxHp` 时才去；买心同理要求 `p.hp + 1 >= p.maxHp`。
2. **治疗绕路没有截止时间**。修复：每层给 45 秒窗口，超时本层放弃该门槛
   （`A._hpGateSince` 按楼层重置）。

修复后 `seed 31` 不再卡在 fount（open 变成 `boss*`），击杀 209 → 112 但那局换了失败模式。

### 第三个 bug：`onlyBossLeft` 要求 `!boss.active`

trace 显示：

```
t=303  open=boss    obj=prism   ← 只剩 boss 房却去拿棱镜
t=456  open=boss*   obj=hunt    ← 进过 boss 房后目标变成追击
```

`onlyBossLeft` 原本带 `!boss.active`，所以**一旦踏入 boss 房（房间变 active）这条规则就失效**，
挂机转头去捡棱镜。已放宽为只看 `!boss.cleared`。

### 解析坑（记下来，免得再踩）

`--verbose --trace` 输出的 `DBG {...}` 行里含有**未转义控制字符**，
`json.loads` 一律报 `Invalid control character`（`strict=False` 也无效）。
可靠做法是**逐字段正则提取**（`"t":(\d+)` / `"openRooms":"([^"]*)"` 等），
不要试图整行 `json.loads`。

## 84. 结论 68：五锁过不了层的**结构性根因**是「DPS < boss 血量」

### 批量统计（12 种子五锁，`openRoomsAtEnd` 构成）

| 现象 | 局数 |
|---|---|
| 结束时含未清 `boss` 或 `boss*` | **11 / 12** |
| 结束时含 `combat*`（激活未清） | 10 / 12 |
| 过第 1 层 | 2 / 12 |

### trace 定位（seed 13）

```
t=531   clr=10  open=boss*  foes=1   ← 只剩 boss 和一个敌人
t=606   clr=10  open=boss*  foes=1   obj=hunt
t=681   clr=10  open=boss*  foes=1   obj=hunt   ← 150+ 秒打不动
```

`foes=1` 持续 150 秒 = **boss 本体打不死**，不是找不到它。

### 数值对照（决定性）

| 项 | 数值 |
|---|---|
| 挂机实际 DPS 中位 | **74**（最大 107）|
| 武器等级 `wlv` | 几乎全为 `{}`（未升级）|
| boss 基础血量 | 1500 / 4200 / 8800（`boss.js:4/6/9`）|
| 首层 boss 实际血量 | `1500 × BOSS_HPM[0]=1.3 × exploreHealthMul × cyst(+25%)` ≈ **2400+** |

**74 DPS 打 2400 血 = 理论 32 秒纯输出**，加上躲避攻击的穿插，实际要 60 秒以上；
而绝境下 5 个修饰符（rage 双倍攻速、deathfight 尸爆接触伤害）让 60 秒站桩几乎必死。

### 所以五锁的真正墙不是「躲不开」，而是「打不动」

这与 §75（锻造房是 56% 概率的随机事件、44% 的楼层没有）形成闭环：

> **没有锻造 → 武器等级 0 → DPS 74 → boss 打不动 → 卡在 boss 房 → 过不了层**

### 方向（下一轮必须解决 DPS）

1. **提高锻造机会利用率**：现在只在「手头武器」满足条件时才去锻造，
   而 `forgeMode='held'`；应改为**只要本层有锻造房且墨水够，就去升当前最强武器**
   （已由 `forgeFirst` 覆盖，但 `wlv` 仍为空 → 需要确认是否真的走到了铁砧）；
2. **武器替换按真实 DPS**（`weaponDps`，当前默认关）在低 DPS 局面下可能有价值；
3. **血清取舍**：`scoreShard` 用固定权重表，应改为按「对当前武器实际增益」排序。

## 85. 结论 69：`close` 血清的 +40% 伤害一直没吃到（距离带 90–150 从来进不了 110）

### 机制（`shards2.js:102`）

```js
if (S.close) { const k = clamp((150 - dist) / 110, 0, 1);
  dmg *= 1 + [0,.2,.3,.4][S.close] * k * (SYN.demol ? 1.5 : 1); }
```

- 距离 **≥150** → 加成 0；
- 距离 **40 及以下** → 满额（+20/30/40%，拆迁协同再 ×1.5）。

而挂机默认交战带是 `[90,150]`（KITE）与 `[40,90]`（FOCUS），
**`k` 在 KITE 下几乎恒为 0**，FOCUS 下也只有一半。

### 修复

拥有 `close` 且不在 α 血清期时，把交战带压到
`[max(26, lo*0.45), min(hi, 110)]` —— 主动贴进加成区。

### 本轮的更大发现：`forgeRooms: 0`（97 次采样全是 0）

在同一批五锁局里，trace 显示 **整局一个锻造房都没有**。
所以 `wlv={}`（武器未升级）不是"挂机不去锻造"，而是**这一层根本没有锻造房**。

结合 §84 的数值对照：

> boss 血量 ≈ 2400（首层，含 cyst +25%），挂机 DPS 中位 **74**
> → 纯输出需 32 秒，实际因躲避拉长到 60 秒以上，绝境下几乎必死。

**因此提升 DPS 不能依赖锻造房（56% 概率、44% 楼层没有），
必须走不依赖楼层的途径：**
1. `close` 血清（本条，已修）—— 已有血清时立刻生效；
2. `sear` 叠层（`shards2.js:103`，同一目标连续命中叠加 +2~4%/层，上限 10~15 层）
   → 需要**集火**而非左顾右盼；
3. `pristine`（`shards2.js:104`，护甲满时 +20~35%）→ 与「满血过层/护甲恢复」策略天然协同。

## 86. 结论 70：`sear` 集火 + `pristine` 保甲——机制正确但**没有提升**（DPS 未变）

### 两项改动

1. **`sear` 集火**（`shards2.js:103`）：同一目标 1 秒内再次命中才叠层（+2~4%/层，
   上限 10、拆迁 15），换目标即重置为 1。实现：拥有该血清时，优先瞄准
   **已带 `searN` 叠层**的敌人（评分 `n*100 - 距离*0.1 + boss 加成`），而不是最近的。
2. **`pristine` 保甲**（`shards2.js:104`）：**双向**——护甲满时 +20%~35% 伤害，
   缺甲则掉到 **0.75x**（lv2 时 0.65x）。实现：拥有该血清时**护甲剩 1 点就撤退**
   （而非等到 0），避免丢掉乘数。

### 实测（五锁，9 种子）

| 种子 | 最深层 | 击杀 | **DPS** | 结束时未清 |
|---|---|---|---|---|
| 1 | **1** | 82 | 67 | combat*,combat,… |
| 3 | 0 | 32 | 61 | combat,combat*,… |
| 5 | **1** | 217 | 99 | combat,combat,boss,… |
| 7 | 0 | 83 | 81 | **boss*** |

- **过层 2/9**，与前一批（2/12）在噪声内，**不作改善宣称**；
- **DPS 仍在 39–99、中位 ~75**，与加改动前**完全一致**。

### 为什么没效果（数据自证）

上一轮已确认 `forgeRooms: 0`（整局无锻造房）。本轮 DPS 依旧 75，说明
**这两项改动的前提——「已经拥有 `sear`/`pristine` 血清」——在绝境五锁里很少成立**：
50 血上限 + 5 个修饰符的压力下，挂机通常只拿到 2–4 个棱镜，拿不到特定血清。

### 结论：DPS 提升不能靠「拥有某血清后的优化」

必须换成**不依赖特定血清**的途径。候选（按可行性）：

1. **武器替换按真实 DPS**（`weaponDps`，现默认关）：低 DPS 局面下换更强的枪；
2. **`scoreShard` 按「对当前武器实际增益」排序**：让有限的 2–4 次选卡尽量都落在伤害上；
3. **集火到死**（不只对有 `sear` 时才做）：缩短单体击杀时间，间接提高清房速度。

### 附：DZMM SSO 调研结论（见 `docs/sso.md`）

- 官方 SDK `dzmm.user.info()` 返回 `{id,name,avatarUrl,token}`，`token` 是 **RS256 JWT（30 分钟）**；
- 但 **`dzmm` 由宿主页注入，只在官方 iframe 内存在**；离线镜像的 shim 正确返回 `null`；
- **可行路径**：在官方页注入工具（`inject.js`）→ 直接拿真实身份显示在 HUD；
- **不可行**（已实测）：游客账号自动创建需要完整指纹且服务端强制人机验证。

## 87. 结论 71：按「武器匹配」给血清加权——**不显著**（且我先踩了一次假对照的坑）

### 动机

`scoreShard` 只用「稀有度 × 流派权重 × 协同」，**完全不看当前武器**。
40 个血清有 12 个 tag（AMMO/ELEMENT/FORM/CRIT/POWER/KILL/HUNT/DASH/MOVE/SURVIVE/ALLY/CURSE），
其中 AMMO 对近战毫无用处、ELEMENT 需要武器本身能挂元素、FORM 在高射速枪上收益更大。
五锁下每局只有 2–4 次选卡，选错就浪费了。

### 实现

按 tag × 武器属性加权（`shardFit`，默认开）：

| tag | 条件 | 倍率 |
|---|---|---|
| AMMO | 近战持有 | **×0.25** |
| AMMO | 有弹匣 | ×1.1 |
| ELEMENT | 武器无元素 | ×0.6 |
| ELEMENT | 武器有 burn/slow/chain/proc | ×1.35 |
| FORM | 高射速(rate≥8) | ×1.25 |
| CRIT | 高射速 | ×1.2 |
| POWER | 单发高(dmg≥18) | ×1.3 |
| KILL | 高射速 | ×1.2 |

### 有效 A/B（配对交错，3 对，五锁）

```
A(不匹配) -89.1 | B(匹配) -110.8
配对差 -21.7 ± 114.3   95% CI [-151.0, +107.6]   ← 跨 0
逐对：(-80, -127.9), (-109.4, -6), (-78, -198.6)   （1 胜 2 负）
→ 无显著差异
```

**按纪律不作改善宣称**，功能保留为可选开关（`shardFit`，默认开，机制上更合理）。

### 必须先记下的坑：我差点把「假对照」当成胜利

第一次比较时我用 `--opt '{"shardFit":false/true}'` 跑了两局，看到
`kills 34 → 154`、`过层 0 → 1`，差点当成大成功。**但当时 `shardFit` 这个选项
根本还没写进 `A.opts`** —— 也就是说两侧跑的是同一份代码，差异纯属批次噪声。

这正是 `AGENTS.md §7` 写的坑（「补丁后必须 grep 新符号」）。
补上选项声明后用 `--opt '{"shardFit":false}'` 验证到 **`unknown autoOpts` 警告为 0**
（选项已生效），才做了上面这个有效 A/B。

**教训：`--opt` 传一个不存在的键不会报错，必须主动确认它被识别。**
