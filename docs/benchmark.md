# [TheSeed] 镜像工具 Benchmark（宏 + 倍速）

> 本文档给出镜像工具的跑分方法与样例数据。所有数据都在**未修改任何游戏源码**
> 的前提下测得：倍速通过重排 `requestAnimationFrame` 的虚拟时间戳实现，
> 宏/自动挂机通过游戏自己的公开输入状态（`Input`）与 DOM 事件驱动。

## 1. 三种基准

| 场景 | 内容 | 关键指标 |
|---|---|---|
| `throughput` | 在一局真实对局中，×8 倍速连续跑 N 秒（性能模式：粒子 15%、关特效、无帧率上限） | `tps`（每真实秒的模拟帧数）、`ratio`（游戏秒/真实秒） |
| `macro` | 回放内置"站桩 30s"操作宏（按住攻击 + 绕圈瞄准），×4 倍速 | `ratio`（宏时间轴对齐精度）、击杀/伤害 |
| `fullrun` | 自动挂机（全自动模式）从新档打到目标无尽深度 | 深度、击杀、受击、结局、真实耗时 |

面板入口：`基准 · BENCHMARK` 三个按钮；命令行入口：

```bash
nix run .#bench -- --kind throughput --seconds 8 --speed 8
nix run .#bench -- --kind macro      --seconds 15 --speed 4
nix run .#bench -- --kind fullrun --seed 7 --policy bloom --goal-depth 1 --speed 8 --timeout 300
```

每次运行输出一行 JSON（`TSW_RESULT …`），`--out results.jsonl` 可追加落盘。

## 2. 样例数据（本机：NixOS，headless Chromium 155，软件渲染）

### 吞吐（throughput）

```json
{"kind":"throughput","speed":8,"seconds":6,"ticks":2879,"tps":479.7,
 "gameS":48,"ratio":8,"inRun":true,"ua":"Chrome/155.0.0.0"}
```

- ×8 档理论值 = 8 × 60 = **480 ticks/s**，实测 **479.7**，误差 < 0.1%；
- `ratio = 8.00`：游戏内时间与真实时间严格 1:8。

### 宏 + 倍速（macro）

```json
{"kind":"macro","speed":4,"seconds":15,"macro":"hold-attack",
 "gameS":25.1,"wall":6.3,"ratio":4,"kills":0,"dmg":0,"ua":"Chrome/155.0.0.0"}
```

- 宏按**虚拟时间轴**录制，回放时与游戏时间严格对齐（`ratio = 4.00`）；
- 站桩宏在起始房没有敌人，所以 kills/dmg 为 0 —— 这是预期行为；
  要测战斗表现请用 `fullrun`。

### 全自动一局（fullrun）

样例（bloom 策略、seed 7、×8、目标无尽 1 层）：

```json
{"kind":"fullrun","speed":8,"seed":7,"policy":"bloom","goalDepth":1,
 "end":"death","gameT":117,"floor":0,"kills":74,"hits":25,"dmg":2570,
 "weapons":["nail"],"shards":{"stat":1,"rnova":1,"rico":1,"fury":1},"syn":0}
```

自动挂机的走位/拿卡策略是"可用"水平，不是人类上限 —— **数据用于策略横向
对比（选卡倾向、武器偏好），不代表任何"人类天花板"**。多次运行的矩阵
（4 策略 × 2 种子）见第 4 节。

> **Firefox 支持**：2026-10-18 已在 headless Firefox 158 验证完整链路——
> boot → 起名 → 选难度 → 自动挂机一整局（`ua: Firefox/158.0`，kills>0）。
> 游戏与全部工具在 Chrome / Edge / Firefox 下均可运行。

## 3. 方法论说明（为什么这些数字可信）

1. **倍速不靠改游戏**：`tools/core.js` 在游戏启动前替换
   `window.requestAnimationFrame`，把虚拟时间戳按倍率推进；游戏的
   `frame(now)` 只看到时间戳，模拟与渲染节拍完全不变。
2. **宏不靠改游戏**：回放重新派发真实 DOM 事件（KeyboardEvent/MouseEvent），
   走的是引擎自己的监听器；坐标按画布矩形换算，分辨率无关。
3. **可复现性**：`TSW.rng.seed(n)` 用 mulberry32 替换 `Math.random`，
   同一 seed 的 fullrun 从洗牌到掉落完全一致。
4. **性能模式只动视觉**：`QS.part/fx/fps`、`SET.shake/flash` 是渲染质量参数，
   不触碰任何游戏数值。

## 4. 构建对比（probe：构造存档 → 模拟无尽深度）

`fullrun` 测的是"挂机从零打到无尽"的全流程；要单独比较**构建（build）**，
用 `probe`：它构造一份带指定武器/血清/芯片的运行存档（走游戏自己的
`loadSave` 校验，不改任何源码），把游戏投放到第 5 章 + 模拟无尽深度，
然后让自动挂机打 N 游戏秒，输出战斗时间归一化的击杀/伤害速率：

```bash
node scripts/headless-bench.mjs --kind probe --depth 5 --seconds 90 --seed 7 \
  --speed 8 --build '{"weapons":["rail"],"wlv":{"rail":3},"shards":{"keen":4,"heavy":5}}'
```

### 深度 5 · 同 seed 对比（自动挂机，战斗时间内归一化）

| build | 击杀/分 | 伤害/分 |
|---|---|---|
| rail + keen4/heavy5/frenzy5/needle3（满锻造） | **54.0** | **1194** |
| nail 裸装 | 40.5 | 825 |
| hail + bloom3/shrap3/ember/fury/leech | 31.4 | 723 |

**结论**（详见 `endless-guide.md`）：高面板武器 + 冻结期输出血清 > 低面板
高频武器硬灌引爆链；bloom 引爆是唯一随深度放大的伤害，但起爆仍靠武器 DPS。
挂机所方差较大（导航/走位占一半因素），精确结论以多 seed 中位数为准。

## 6. 躲弹幕测评（dodge benchmark）

专门测"闪避"这一项能力，而不是整局综合强度。做法：**禁止开火**（`noFire`），
让敌人不会减少，再按固定节拍**持续补充远程敌人**（gunner/sniper/turret/mortar，
保底 7 个），于是弹幕只会越来越密 —— 这是一场纯挨打压力测试。

指标：

| 指标 | 含义 | 方向 |
|---|---|---|
| `hitsPerMin` | 受击次数 / 游戏分钟 | 越低越好 |
| `dangerAvg` | 站位处威胁值均值（预警圈+弹道预测+虚空区+地刺） | 越低越好 |
| `hazardPct` | 威胁值 ≥1.2 的 tick 占比（暴露率） | 越低越好 |
| `clearAvg` / `clearP5` / `clearMin` | 所选方向上"最坏一枚子弹"的横向余量（均值 / 5% 分位 / 最小值） | 越高越好 |
| `dashesPerMin` | 冲刺频率 | 参考 |

归一化用**实测 play tick 数**（`ticks/3600 = 游戏分钟`），而不是 `G.runT`——
后者在自动重开时会归零，早期版本用它算出了 4440 次/分的荒谬数字。

| 种子 | v2 受击/分 | v1 受击/分 | v2 危险值 | v1 危险值 | 胜 |
|---|---|---|---|---|---|
| 11 | **15.1** | 22.2 | 4.138 | 1.698 | v2 |
| 23 | 22.4 | **22.0** | 3.356 | 5.68 | v1 |
| 41 | **9.2** | 21.2 | 0.734 | 3.367 | v2 |
| **平均** | **15.6** | 21.8 | — | — | — |

- 三个有效种子中 v2 赢 2 个（平均 **15.6 vs 21.8** 次/分，约 **-29%**）；种子上限只有 3 个，
  单种子可翻转，所以结论按平均值看，不要当成显著性证明；
- 来源：v2 把"最坏一枚子弹的横向余量"（`laneClear`）算进评分，避免两侧同时被夹，

## 9. 实力期望与方差（5 种子实测）

同配置（bloom 流派 · classic · 目标无尽 1 层 · ×8 倍速 · 全自动）跑 seed 11/23/41/57/73：

| 指标 | 均值 | 标准差 | 最差 | 最好 |
|---|---|---|---|---|
| 存活（游戏秒） | 267 | ±81（CV 30%） | 163 | 389 |
| 击杀 | 41.2 | ±14.4（CV 35%） | 21 | 59 |

- 方差主要来自**开局房间构成与掉落**：拿到能配合的血清（bloom/shrap/frenzy）就滚起来，
  拿不到就死在第一章；
- 另有两个种子触发了 `stall`/`replan` 计数（4/14 与 8/25），即仍有少量绕圈重算，
  但都被兜住（没有卡死：两局都正常推进到死亡）；
- 复现：

```bash
for s in 11 23 41 57 73; do
  node scripts/headless-bench.mjs --kind fullrun --seed $s --policy bloom \
    --goal-depth 1 --speed 8 --timeout 200 --out .tmp/var.jsonl
done
```

跑多局会额外输出一行 `{"kind":"summary", ...}`（均值/标准差），便于对比改动效果。

### 被数据否掉的方差假设（留档，避免重复踩）

| 假设 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 开局先堆生存能压方差 | 首层且血清 <2 时，plate/vital/quick/swift/leech 权重 ×1.45 | seed 23/41/57 的 gameT 264/251/268 → **200/206/173**，击杀 40/36/59 → **25/31/8** | **否**：标准差从 80 降到 18，但均值塌了——"稳定地更差"，已回滚 |

原因分析：首层防御血清挤压了输出位，清怪变慢 → 房间拖长 → 弹幕叠满，反而更容易死。
下一个该试的方向是**反方向**（首层 DPS 偏向）或直接治理"清怪速度"而非生存。

## 10. 绝境五锁基线（目标①的起点）

五个修饰符全开：`rage`（敌人攻击频率 ×2）、`deathfight`（致命伤后 2 秒不可选中）、
`bulwark`（敌人进战后 20 秒减伤 20%）、`rot`（免疫燃烧/中毒/冰冻）、`cyst`（敌人生命上限 +25%）。

**怎么让修饰符进入基准局**（踩过三个坑，记下来）：

1. `modifiers.js` 的 `PENDING_MODIFIERS` 是它自己作用域里的 `let`，bench 里赋值只会遮蔽，
   改不到游戏；`sortie()` 又会走营地而不是直接开局。
2. 正解是**构造存档**：`{v:1, floor:0, diff:'despair', modifiers:[五锁], …}` → 交给游戏自己的
   `loadSave()` → `cleanModifiers(s.modifiers, s.diff)` 校验 → `resumeRun()`。
3. `STORE.setItem` 在 `STORE.locked` 时会**静默丢写**，必须直写 `STORE.mem` + `dirty`。
4. `whenGame()` 只等 `game.js`（脚本序号 25/76），而 `newRun()` 里调用 `takeRunModifiers()`
   定义在 `modifiers.js`（序号 70/76）→ 开局太早会 `ReferenceError`。基准必须先等脚本就绪。

结果行会回显 `modifiers: [...]`（开局）与 `modifiersAtEnd`，可据此确认五锁真的生效。

### 三轮迭代（seed 7 / 23 / 41，rounded，×8，各 150 秒，同种子同配置）

| 种子 | 原始基线 T/kills | +死斗识别 T/kills | +清房追击 T/kills |
|---|---|---|---|
| 7 | 198 / 9 | 158 / 15 | **357 / 21** |
| 23 | 136 / 11 | 267 / 17 | **255 / 25** |
| 41 | 111 / 86 | 389 / 59 | **357 / 112** |
| **均值** | **148 / 35.3** | 271 / 30.3 | **323 / 52.7** |

**两处改动**（都在 `tools/auto.js`，未动上游）：

1. **死斗敌人当危险源**：绝境「死斗」修饰符下，`deathFightLeft > 0` 的敌人**不可选中但仍每帧造成接触伤害**
   （`enemies.js:115` 没有过滤它）。原来挂机在 `nearestEnemy` 里把它们整个跳过 → 站在它们旁边挨打却不躲。
   现在不瞄准它，但纳入威胁场驱离。存活 **148 → 271 秒**。
2. **清房追击**：房间清空条件是无未死敌人（`game.js:229`），只要有一个漏网的（躲墙后、`rot` 免疫 DoT、
   够不到）整局就停摆。实测探针看到「敌人只剩 1 个、击杀数 50 秒不动」。
   现在：房间激活但**没有可射击目标**时，0.5 秒后主动朝最近敌人逼近。
   存活 271 → **323 秒**，击杀 30 → **53**。

两处都是**存活与击杀同向改善**（不是拿命换输出），所以是实质进步。

**试过但未采纳的变体（留档）**：把「直追」升级成「BFS 绕到能射到的格子」

| 变体 | 3 种子均值 |
|---|---|
| 直追（采纳） | 323s / 52.7 杀 |
| 纯绕路（每 0.9s 重算） | 230s / 52.7 杀 ← 明显变差 |
| 卡住才绕（1.2s 无进展才 BFS） | 284s / 54.7 杀 ← 落在 ±30% 噪声内，无法证实 |

单局方差 CV≈30%，这种量级必须多种子且差距显著才算数；绕路会打断瞄准/DPS，
所以保留直追。

**另一条未采纳**：门框卡位加「3 秒无击杀就主动出击」

| 变体 | 3 种子均值 |
|---|---|
| 无限卡门（采纳） | 323s / 52.7 杀 |
| 3s 超时出击 | 244s / 37.3 杀 ← 均值下降，回退 |

探针确实看到单只精英卡门 32 秒（`doorfunnel`、击杀冻结），但在绝境里卡门
本身是**生存手段**：放弃则会同时面对多个敌人，存活掉得更快。
所以「卡门太久」的诊断是对的，但解法不是取消卡门。
原始数据：`docs/data/despair-fivelock.jsonl`。

## 11. 入侵抵抗基线（目标②的起点）

入侵抵抗（`RUN_MODE='invade'`）是 Brotato 式竞技场：20 波、最多 6 把武器自动开火、
波间有商店/补给/升级。**挂机不认识它的界面状态**（`ivrole` / `ivstart` / `ivlv` /
`ivcrate` / `ivshop`，统称 `IV_UI`），所以直接开局会软锁。

**能测起来的最小通道**（`--kind invade`）：

1. 构造 `achroma_ivrun` 存档（`{v:1, diff, iv:{wave, role, w:[{id,t}], …}}`），
   字段由游戏自己的 `ivLoadSave()` 逐项校验（`wave` 1..19、`role` ∈ `IV_ROLES`、
   `w[i].id` ∈ `IV_W`、`t` 0..3）。
2. 直写 `STORE.mem`（`STORE.setItem` 在 `locked` 时静默丢写）→ `ivResume()`。
3. `ivResume()` 结束后 `G.state='ivshop'`；用游戏自己的 `ivNextWave()` 进战斗，
   状态路径会打印成 `ivshop → play`。
4. 关掉 `autoRestart`，否则死亡会被自动重开，样本变脏。

**结论**：绝境入侵下挂机稳定卡在**第 6 波**（起始第 5 波＝撑过 1 波多），
三颗种子一致，说明这是结构性瓶颈而不是随机波动。目标②的起点就是 6 波 / 20 波。

### 五锁的真实瓶颈（探针实测，2026-10-27）

对 seed 7 做了逐帧探针（每 2 秒采样），一条典型局的轨迹：

| 游戏秒 | 护甲 | 血 | 击杀 | 场上敌人 | 状态 |
|---|---|---|---|---|---|
| 44–76 | 3 | 5 | **9（冻结 32 秒）** | 1（精英，距离 >60） | `doorfunnel` |
| 83–111 | 3→1→2→3 | 5 | 10→21 | 最多 6 | 正常交火 |
| 118 | 3 | 5 | 21 | 0 | 选卡 |
| 130–144 | 3 | 5 | 22→23 | 1–4 | 继续 |

两条硬结论：

1. **血几乎不掉，护甲在反复吸收**（`hits` 缓慢上升但 `hp` 一直是 5）——
   说明死因不是「被磨死」，而是**清不完**（波次/房间拖住）。
2. **全程只有一把 `nail`、零血清**（`sh:0` 直到 t≈122）——
   `bulwark`（敌受伤 -20%）+ `cyst`（血量 +25%）双重压制下，
   初始钉枪 DPS 完全磨不动，这才是卡住的根因。

对应地，本轮试的两条「减少空等」的改动都被数据否决（见上）：
问题不在等待策略，而在**输出不足**。下一轮方向：让挂机在绝境里**优先确保拿到输出型血清/更好武器**
（而不是继续磨），必要时把「清不动就换目标去拿资源」作为一等策略。

## 12. 方法论纠错：3 个种子不足以判定改动（重要）

前面几轮我用 **seed 7/23/41（3 个种子）** 做前后对比，并据此宣布过
「148s → 323s 是实质进步」。把种子扩到 6 个重测同一配置后：

| 配置 | n=3 均值 | n=6 均值 |
|---|---|---|
| 五锁基线（当前代码） | 323s / 52.7 杀 | **214 ± 70s / 40.7 ± 47.7 杀** |

**n=3 的 323s 是高估了 50% 的抽样结果**。按 n=6 的标准差计算：

> 单局 gameT 标准差 70s，n=6 的 95% 检测下限 ≈ **79 秒**。
> 也就是说，任何小于 ~80 秒（约 37%）的均值差异，用 6 个种子**根本测不出来**。

### 这条纠错带来的操作规则

1. **改动验收至少 6 个种子**（7/23/41/57/73/91），并且要和同批次重测的对照组比，
   不能和跨批次的历史数字比（批次间环境/负载也不同）。
2. 报告必须带 **± 标准差** 和样本数，不给单点数字。
3. 一次跑 3 个种子得到的“提升”只能当**方向性信号**，不能当结论——
   本文件 §10 里被否决的三个微优化，和“被采纳”的那次，都要按这条重新理解。
4. 想检测 <20% 的改动，n 需要 20+；单局约 50 秒真实时间，即一次 A/B 约 20 分钟。

原始数据：`docs/data/despair-fivelock-6seed.jsonl`（6 行，含每种子明细）。

## 13. 零位移死局与导航硬兜底（含 6 种子结果）

### 症状（seed 91 复现）

用调试镜像（`?trace=1` 时每 3 游戏秒打印 `TSW.auto.dbg`）看到一局**完全停下**：

```
 "px":1023,"py":1386, "vial":809, "wp":[216,1448], "note":""}
```

1. `pickObjective` / `drivePlay` 增加 **WORLD 就绪守卫**（地形未生成时不追目标）；
2. **导航硬兜底**：导航状态下若 **2.5 秒零位移**，强制沿一个 pit/void 安全的方向
   冲 1.2 秒（计入 `stall` 指标），打破死局。

- 存活 +45s **低于 79s 检测下限，统计上不显著**；

## 14. 基准是非确定性的（决定性发现，推翻前面所有 A/B 的精度）

**实测**：同一个种子（91）连续跑三次，配置完全相同：

| 次 | 游戏秒 | 击杀 | stall |
|---|---|---|---|
| 1 | 147 | 0 | 56 |
| 2 | 296 | 28 | 49 |
| 3 | 461 | 30 | 52 |

**同一 seed 差 3 倍**。原因在 `site/js/game.js:693`：

```js
const rdt = Math.min(.05, Math.max(0, (now - last) / 1000)); last = now;
```

每帧的 `dt` 来自**真实经过时间**，而游戏里所有积分型逻辑
（`p.vx = lerp(p.vx, mx*spd, Math.min(1, dt*14))`、弹道、AI 转向、相机）都依赖它。
倍速工具只是让每帧步进变快，**并不会把 `dt` 固定**。

`TSW.rng.seed()` 只替换了 `Math.random`（覆盖 265 处调用），
所以**随机数可复现，物理不可复现**。

### 这推翻了什么

- §12 的「6 种子检测下限 79 秒」只在**同批次同负载**下成立；
- 所有跨轮次 A/B（包括我宣布过的「148s → 323s」「214 → 259」）都不可比，
  因为它们跨了批次、负载也不同；
- 想得到可比数字，必须**同一批次内交错跑对照组与实验组**（A/B/A/B…），
  并且报告同批次的相对差值，而不是跨批次均值。

### 正确的测量协议（后续必须遵守）

1. 一次会话内，**交错**跑 `baseline, candidate, baseline, candidate, …`
   各 N 局（N≥5），用**配对差**的均值和标准差判断；
2. 每组前后必须**同机同负载**（不要一边跑基准一边做别的事）；
3 报告 `配对差均值 ± 标准差`，而不是两个独立均值；
4. 想要 20% 精度，配对差样本需要 ~15 对以上。

在没做到这些之前，任何「提升 X%」都只能算**传闻**，不算结论。

## 15. 配对 A/B 工具与第一批结论（`--kind ab`）

按 §14 的协议实现了 `--kind ab`：**同一浏览器会话内交错跑 A/B/A/B…**，
输出配对差 ± 标准差、SEM、95% 置信区间、t 值和判定。

```bash
nix run .#bench -- --kind ab --rounds 5 --diff despair \
  --mods rage,deathfight,bulwark,rot,cyst --speed 8 --seconds 15 --timeout 70 \
  --optA '{"autoOpts":{"navFallback":false}}' \
  --optB '{"autoOpts":{"navFallback":true}}'
```

`--optA/--optB` 是 JSON，`autoOpts` 会临时覆盖 `TSW.auto.opts` 的同名项并自动还原。

### 第一个结论：导航兜底**无效**（推翻上一轮的 +45s）

| 指标 | 值 |
|---|---|
| A（兜底关）均值 | 223 秒 |
| B（兜底开）均值 | 232 秒 |
| **配对差** | **+9.2 ± 83.6**（SEM 37.4） |
| 95% CI | **[-64.1, +82.5]** ← 横跨 0 |
| t | 0.25 |
| 判定 | **无显著差异** |
| 击杀配对差 | -43.8（配对差极大，逐对看正负都有） |

**上一轮用 6 个独立种子得出「214 → 259 秒」，在配对测量下不成立。**
原因正是 §14 说的：独立样本的方差里混入了批次/负载差异，配对测量把它抵消了，
于是看到「兜底对存活几乎没有作用」。

### 这条结论的意义

- 兜底值不值得保留？**它不伤**（CI 横跨 0），而且能解开「零位移死局」这类极端情况，
  所以**保留但不再当作性能优化**；
- 真正要解决的是 `pickDir` 为什么会在某些位置全负分——那需要的是
  「局部无解时选最接近目标的可行方向」的逻辑（已有初版 + 绝对兜底），
  而不是靠随机冲刺；
- 后续所有改动**一律用本工具测配对差**，CI 跨 0 就不算改进。

## 16. 入侵抵抗有了专属挂机逻辑（首次）

### 之前为什么打不了

`tools/auto.js` 里 **`invade` 出现 0 次**——挂机只知道突入探索（房间图、门、交互物、
目标探索）。入侵是 Brotato 式竞技场：一个封闭场地、一波一波敌人、每波限时存活。
实测 trace：

```
{"world":"40x26 rooms=1","active":false,"inter":0,"obj":null,"note":"","px":328,"py":216}
```

`active:false`（没有“激活房间”概念）、`inter:0`（没有交互物）、`obj:null`（无目标），
于是挂机在**无目标状态下游走**，这就是入侵卡在第 6 波的真正原因，而不是某个参数没调好。

### 新增 `driveInvade()`

`G.mode === 'invade'` 时走独立分支（不碰房间/门/交互物）：

1. **瞄准最近的敌人**（入侵靠武器自动开火，只需 `Input.mx/my` 瞄准）；
2. **保持射程带**：`band [55,110]`，首领波（wave%5==0）放大到 `[70,130]`；
   太近则后撤、太远则接近、在带内则横向绕行；
3. 场上无敌人时**向场地中心漂移**，避免贴墙；
4. 威胁值 ≥1.6 时冲刺脱离；所有移动都过 `pickDir`（含 24 方向威胁场）。

### 实测（从第 9 波起，despair，rounded，×8）

| 次 | 到达波次 | 击杀 | 存活 |
|---|---|---|---|
| 1 | 10 | 11 | 12.9s |
| 2 | 10 | 12 | 10.5s |
| 3 | 10 | 22 | 12.5s |

**结论（诚实）**：击杀从 ~9 提升到 11–22，说明它真的在打；但**一波（~25s）撑不到 1/3**
就死，仍然卡在第 10 波。生存能力是下一个要解决的问题（很可能是第 9 波敌人密度 +
挂机只会「保持距离」而不会「利用场地边缘/绕大圈风筝」）。

### 入侵 A/B 的指标分辨率问题（工具坑）

用 `--kind ab --ab-kind invade` 测开关时，A/B **都到达同一波次**（6 vs 6、10 vs 10），
配对差恒为 0，指标没有分辨率。已修两处：

- 零方差时的判定不再误报「A 更好」，改为「完全无差异（指标无分辨率）」；
- 入侵 A/B 默认从**第 9 波**起跑（原来 5 波太容易，全部 6 波），提高分辨率。

但即使从第 9 波起，只要挂机稳定死在同一波，波次指标依然无分辨率——
后续入侵调优应当改用**存活秒数**（或「波内存活比例」）作为指标。

## 18. 入侵：起始波决定了「看起来卡在哪」（关键测量纠错）

加了波间商店自动化后重测，发现之前「卡在第 6 / 第 10 波」的判断**是起始波造成的错觉**：

| 起始波 | 到达波 | 存活秒 | 击杀 |
|---|---|---|---|
| 1 | 4 | 56.6 | 129 |
| 5 | 6 | 25.5 | 75 |
| 7 | 8 | 6.7 | 13 |
| 9 | 10 | 6.7~12.9 | 13~21 |

规律：**从第 N 波起跑，大约只能再推进 1–3 波**。这不是「卡在第 X 波」，
而是**绝境难度下入侵的强化曲线极其陡峭**——每过一波，敌人强度跳得比挂机成长快。

由此产生两个测量结论：

1. 之前「从第 5 波起跑 → 卡第 6 波」被误读成「第 6 波是结构性瓶颈」，其实是起点选得高；
2. 入侵模式的 A/B 若用「到达波次」比较，会因起点不同而完全失真；
   用 `survived`（波内存活秒数）才对，且**必须固定同一起始波**（现固定第 9 波做高难验证，
   或用第 1 波做「从零能走多远」的长期能力评估）。

### 真正的瓶颈：成长速度 < 难度增长

从第 1 波起跑能打 129 杀 / 56 秒到第 4 波，说明**挂机在早期是能打的**；
后面崩掉说明挂机的成长（武器等级/物品/属性升级）跟不上绝境曲线。
本轮已加入的波间自动化覆盖：

- `ivcrate`：补给箱（Enter 领取）；
- `ivlv`：升级选项按优先级挑（dmg > aspd > crit > range > hp > speed > …）；
- `ivshop`：按「武器 > 伤害类 > 生存类」优先级购买可负担的报价，然后 `ivNextWave()`
  （游戏侧的 `ivBuy` 自带武器槽/物品上限/付款校验，所以自动点击是安全的）。

但**绝对强度仍不足**：绝境第 4 波以后就崩。下一步要针对「成长」：
优先买武器等级/合成（`ivCombine` 三合一升阶）、优先经验与材料掉落。

## 19. 结论 3：入侵「武器合成」是**确定的改进**（通过 CI，且 4/4 全胜）

### 先修了一个让所有入侵 A/B 失真的 bug

`--start-wave 1` 之前**没有真正传进页面**：yargs 把 `--start-wave` 解析成
`args['start-wave']`，而驱动读的是 `args.startWave` → 永远取不到 → A/B 实际一直在
**第 9 波**起跑。于是「合成」这种成长型改动根本来不及生效，
测出来是「无显著差异（-0.6±5.5）」。

修好之后（同一起始波、同会话交错、顺序交替）：

```
A（不合成）56.3s | B（合成）61.6s
配对差 +5.3 ± 1.6     95% CI [+3.7, +6.9]      ← 不含 0
逐对：55.8→60.0, 58.5→62.2, 55.6→61.6, 55.2→62.4  （4/4 全胜）
判定：B 更好
```

**这是三档目标里第二条通过统计检验的机制性改进**（第一条是入侵模式用冲刺）。

原因：入侵的伤害主要来自「武器阶数」而不是件数，`ivCombine` 把三件同名同阶合成
+1 阶；绝境里每波敌人强度跳得快，阶数跟不上就崩。

### 实现（`driveInvadeUI` 的 ivshop 分支）

在买之前先**扫一遍武器列表做合成**（`ivCombine` 自带「同名同阶 + t<3」检查，
直接调用安全），然后再按「武器 > 伤害类 > 生存类」买可负担的报价，最后 `ivNextWave()`。
开关：`A.opts.invadeCombine`（默认开）。

原始数据：`docs/data/ab-invade-combine.txt`。

### 顺带确认：会话漂移不存在

同一会话连续跑 4 次入侵（第 1 波起）：47.8 / 49.9 / 47.2 / 48.6 秒，100~117 杀，
**高度稳定**。所以 A/B 的配对设计是可靠的——之前的问题纯粹是参数没传进去。

## 25. 结论 11（仍不显著）+ 长跑揭示的方差真相

### 先修了测量口径：入侵现在「跑到死亡」

之前固定 60–150 秒窗口，样本永远以 `alive` 结束（实测真实死亡在第 5 波 / 127 秒附近），
对后期改动没有分辨率。现在 `runInvade` 会一直跑到 `G.state === 'dead'`（或墙钟预算耗尽）。

### 长跑重测「升级：dps vs growth（收获/幸运优先）」

```
A(dps) 184.0s | B(growth) 224.8s
配对差 +40.8 ± 77.5   SEM 44.8   95% CI [-46.9, +128.6]   ← 跨 0
逐对：151.7→281.8 (+130.1), 160.8→151.2 (-9.6), 239.5→241.5 (+2.0)
击杀配对差 +97.3
```

**仍不显著**，但要注意：

- 方向和机制一致（`ivGainMat` 同时给钱+经验，`luck` 直接乘每击杀掉落）；
- 均值被**单对 +130** 拉起来，另两对几乎是平的 → 典型的「偶尔滚起来」；
- 这说明 growth 策略**有上限收益但触发不稳定**，而不是无效。

### 顺带修正天花板

长跑实测存活 **150~282 秒**（不是之前说的 127 秒定值），对应波次 5–7。
所以入侵的真实天花板是一个**很宽的区间**，本身方差极大——这也是为什么
入侵的小改动几乎都无法通过 CI：**噪声 > 效应**。

### 结论：入侵需要的是「降方差」而非「提速」

连续 8 项入侵改动里只有 4 项通过，且通过的 4 项都比未通过的**效应更大**（+1.6~5.3s vs ±2s）。
要在剩下来的改动里测出差异，必须先把方差压下来：
- 固定开局（同样的前 3 波选择序列，减少随机掉落影响）；
- 或把「每对」改成同一局存读档的 A/B（真正同源比较）。

```
A(直接清房) 288.0s | B(资源优先) 286.1s
配对差 -1.9 ± 147.1    SEM 52.0    95% CI [-103.8, +100.1]    t = -0.04
逐对符号：- + - - + + + +                     （4 正 4 负）
```

**结论：不采纳，默认保持 `exploreOrder='fight'`。**

### 这条记录真正的价值：量化了五锁测量的极限

- 单局 `gameT` 标准差 ≈ **147–208 秒**；
- 8 对时 CI 半宽 ≈ **104 秒**；
- 因此要检出「真实的 +50 秒改进」，需要 **n ≈ 35 对**（约 70 次全局长跑，数小时）；
- 这解释了为什么本轮之前所有五锁 tweak 都不显著：**不是改动无效，而是测量不够**。

1. **局部指标替代全局指标**：例如「单房间清场秒数」「每 100 秒击杀数」
   这类几百个样本/局的量，方差远小于「整局存活」；
2. 或者**固定开局种子 + 固定房间布局**，把随机性压到只剩操作差异；
3. 全局 `gameT` 只用于「是否崩坏」的粗筛，不再用于判定优劣。

## 27. 结论 13：局部指标已接入，但「击杀率」同样不稳定（符号会反转）

### 已实现的局部指标（`runFullRun` 每 250ms 采样）

| 字段 | 含义 |
|---|---|
| `roomClears` | 本局成功清场的房间数 |
| `roomClearMean` / `roomClearMax` | 清场耗时均值 / 最大值（游戏秒） |
| `killPer100` | 每 100 游戏秒的击杀数（滑动窗口） |

A/B 支持 `--metric roomClearMean|killPer100|gameT`。

### 实测：同一改动、同一指标，两次符号相反

用 `killPer100` 比较「资源优先 vs 直接清房」：

| 批次 | 窗口 | A(fight) | B(resources) | 配对差 | 95% CI | 判定 |
|---|---|---|---|---|---|---|
| 5 对 | 20 s | 8.1 | 33.4 | **+25.3 ± 27.4** | [1.3, 49.3] | B 更好（曾“通过”）|
| 6 对 | 10 s | 16.4 | 6.9 | **-9.5 ± 15.2** | [-21.7, 2.6] | 无显著差异 |

**同一改动、同一指标、只改了采样窗口和样本数，结论就翻了个面**。逐对数据还出现多个 `0` 值
（短局里 10s 窗口落空，没有击杀），说明该指标在「局短 + 死亡早」时不稳定。

### 教训（写进方法论）

1. 「局部指标方差更小」这个假设**未经证实就不能用**。清场样本实测每局只有 1–2 个，
   击杀率窗口也只有十几个，和整局 `gameT` 在同一量级上都不够；
2. 指标必须**先验证自身稳定性**：同一组配置跑两遍，看指标均值/符号是否一致，
   再拿它做 A/B；
3. 目前五锁下**没有任何指标**被证明能分辨 <50% 的差异。
   因此在拿到稳定指标之前，五锁侧的「优化」都只能是推测。

### 下一步（明确）

1. 增加**单局样本密度**：不再「一局一个数」，而是把每局的清场耗时、每 10s 击杀
   全部记录成数组落盘（`docs/data/`），做分布比较而非均值比较；
2. 用 **Wilcoxon/自助法**这类非参数检验替代均值 CI（对长尾更稳）；
3. 或者接受现实：五锁通关可能不是靠微调能达到的，需要**结构级改变**
   （例如给挂机加“集火/撤退/绕后”的状态机，而不是继续调权重）。

原始数据：`docs/data/ab-killper100-20s.txt`、`docs/data/ab-killper100-10s.txt`。

## 28. 结论 14：结构级改动（战斗状态机）也没能通过——方差彻底压过效应

### 做了什么

把原来逐帧的临时战斗判断（护甲阈值 + 距离带）换成**三态状态机**，带滞回：

| 状态 | 进入条件 | 行为 |
|---|---|---|
| `RETREAT` | 护甲破且未恢复 / 低血 | 拉远 170~250，**不开火** |
| `FOCUS` | 场上 ≤3 敌且血量健康 | 压到 40~90 抢输出 |
| `KITE` | 其它（人海） | 保持 90~150 绕行 |

带滞回窗口（0.6~0.8s）避免边界抖动；`A.opts.fightSM` 可切换回旧逻辑做 A/B。

### 6 对结果（五锁，90 秒窗）

```

配对差 -33.2 ± 136.1   95% CI [-142.1, +75.7]    ← 跨 0

```

**不显著，且方向为负**。默认改为 `fightSM: false`（未经证实的行为不设为默认）。

### 这是第三个「结构级改动也无法判定」的证据

| 尝试 | 类型 | 结果 |
|---|---|---|
| 资源优先（改目标顺序） | 结构级 | 8 对后符号对半 |
| 视距/冲刺/合成/买武器（入侵） | 机制级 | 4 条通过（效应 1.6~5.3s，成对一致） |
| 战斗状态机 | **结构级** | 6 对 CI 仍跨 0（±136s） |

规律：**入侵的改进能测出来（因为单局短、方差相对小），探索五锁的改进测不出来
（单局 200~440 秒、SD≈150）。**

### 诚实的现状与建议

- 目标①（绝境五锁通关）**在本会话的测量能力下无法通过 A/B 调优推进**；
- 要推进只有两条路：

     这样同 seed 就是同结果，A/B 方差会骤降到近 0）← 技术可行、价值最高；
  2. 放弃 A/B，用「多打几十局看能否偶然通关」的方式碰运气（不可取）。

原始数据：`docs/data/ab-fight-sm.txt`。

## 29. 结论 15：确定性模式把方差降了约一半，但**没有做到可复现**

### 实现（`core.js` 的 `TSW.det`）

游戏用真实经过时间算 dt（`game.js:693`），所以同 seed 也跑出不同结果。
`det` 模式给游戏一条**严格按 16.667ms 递增**的虚拟时间轴，每帧固定一个 tick：

```js
if (det) {
  acc += dt * Math.max(1, speed);
  while (acc >= VIRT_DT && steps < MAX_STEPS) { acc -= VIRT_DT; virt += VIRT_DT; fireTick(); steps++; }
  if (steps >= MAX_STEPS) acc = 0;
  return;
}
```

另加 `TSW.det.ticks` 计数与「按 tick 预算收尾」（默认 18000 tick = 300 游戏秒）。

### 实测（五锁，seed 7，同配置跑 3 次）

| 次 | ticks | gameT | kills | dmg | 结局 |
|---|---|---|---|---|---|
| 1 | 16333 | 260 | 47 | 2821 | death |
| 2 | 10070 | 159 | 34 | 3295 | death |
| 3 | 18037 | 297 | 36 | 2409 | timeout |

**对比非 det 模式**（同配置历史数据：gameT 200~440、SD≈150）：

- 方差**降了一半左右**（本轮 159~297，SD≈72）；
- 但**仍然不可复现**：同一 seed 三种结局，因为 `MAX_STEPS` 截断取决于机器负载，
  「哪些帧被截断」是真实时间的函数 → tick 序列仍然不同。

### 结论与取舍

- `det` 模式**值得保留**（方差减半是实打实的），已接 `--det 1`；
- 但它不是「完全可复现」，因此**仍需配对 A/B**，只是所需样本数减半；
- 要做到真正可复现，必须让**每帧恰好一个 tick 且不丢弃**
  （即 `steps` 永远 =1、`acc` 永不溢出）——这要求把倍速拆成「多帧渲染、单 tick 逻辑」，
  是一次结构性改造，超出本轮范围。

### 现状总结（目标①）

| 手段 | 状态 |
|---|---|
| 配对 A/B | 已实现，但五锁单局 SD≈70~150，需 ~35 对才能测 +50s |
| 确定性模式 | 已实现，SD 减半（≈72），仍不可复现 |
| 局部指标 | 已实现，但自身不稳定（符号会反转） |
| 结构级改动（状态机/资源优先） | 都做了，都测不出 |

## 30. 结论 16：修复两个会让**所有 A/B 结论失效**的 bug（NULL 测试的价值）

方法：跑一组「两臂完全相同」的 A/B（`optA == optB`）。正确结果是「无显著差异」。
任何偏离都说明 A/B 本身有偏置。

### bug 1：`det` tick 计数没有按局重置

`TSW.det.ticks` 是全局累计，第一局用完后第二局的「tick 预算」开局即满，
于是 A/B 里第 2 局开始 `gameT` 只有 **2~3 秒**（NULL 首测实测 `145 → 3`）。
修复：每次 `runFullRun` 记录 `detT0 = ticks`，预算用 `ticks - detT0`。

### bug 2（致命）：顺序交替时**臂标签没有换回来**

为抵消会话漂移，我把每对改成「A→B / B→A」交替，但比较时仍把「先跑的」当 A 臂。
于是**每一对翻转的符号都是错的**——真实 A/B 的结论会被系统性地反转。

NULL 测试直接暴露了它：

```
修复前（两臂完全相同！）：delta -63.0 ± 39.5   95% CI [-101.7, -24.3]   → 判定「A 更好」
逐对：(289,217,-72), (257,145,-112), (214,196,-18), (293,243,-50)
```

**两臂完全一样却「显著」判定 A 更好** —— 这就是标签错位的指纹。
修复：`const a = flip ? second : first; const b = flip ? first : second;`

```
修复后：delta +10.5 ± 82.9   95% CI [-70.7, +91.7]   → 「无显著差异」✔
逐对：(278,287,+9), (245,144,-101), (88,185,+97), (194,231,+37)
```

### 这两个 bug 意味着什么

- 本会话之前**所有**用 `--kind ab` 得出的结论（含 4 条「通过」的入侵改动）
  都可能被 bug 2 的符号反转污染——**必须重测**；
- 新增 `warmup`（首局丢弃）用来消除「首局冷启动」噪声，实测稳态三对仅差 ±3 秒；
- 现在的标准做法：**先跑 NULL 自检，通过了才采信 A/B 结果**。

## 40. 结论 25：导航兜底**从来没有生效过**（被 navigation 覆盖）+ 修复

### 诊断（`?trace=1`，classic，seed 7）

t=186 至 t=219（30+ 游戏秒）玩家坐标**固定在 (613,924)** 完全不动，
目标是 414px 外的「实验血清」，路标 `wp=[456,808]`，`note` 为空。

### 根因：兜底写在了 navigation **之前**

```js
// 旧代码（drivePlay 内，navigation 之前）
if (A._forceUntil && G.time < A._forceUntil && A._forceDir) { mx = A._forceDir[0]; my = A._forceDir[1]; }

} else if (dl > 12) { [mx, my] = pickDir(p, dx, dy); }   // ← 把兜底覆盖掉了
```

```js
if (A._forceActive) { mx = A._forceActive[0]; my = A._forceActive[1]; }
```

## 42. 结论 27：`forgeMode='any'` 是**明确的负效果**（过层率 0/5 vs 3/5）

| 配置 | 过层率（5 种子） | 备注 |

### 为什么 `any` 有害（机制解释）

`'any'` 会让挂机只要**任意已装备武器**可升级就去锻造，包括副武器（常常是低阶、
甚至评分很低的枪）。这导致：

1. 墨水被花在**弱的副武器**上（+25% × 低基数 = 几乎无收益）；
2. 挂机为锻造反复跑图，**清房时间被挤占**；
3. 主武器的升级反而被推后。

所以「钱花在武器上」这条规律要加限定：**要花在主武器（当前火力来源）上，而不是任何武器**。

### 方法层面的收获（第二次验证）

| 指标 | 能否分辨 |
|---|---|
| `gameT`（连续、SD 70–150） | 不能（本例把 0/5 vs 3/5 显示成 -9s）|
| 过层率（二元） | **能**（0/5 vs 3/5，5 种子即清楚）|

**今后一律先跑过层率，再用 gameT 看细节。**

### 机制解释

在绝境/经典里，**清房时间是硬约束**（波次/房间拖着就会被淹）。所以：

1. 任何「为了升级武器而额外跑图」的行为都在**挤占清房时间**；
2. `held` 之所以最优，是因为它**只在顺路时**（手持武器刚好能升）才去，几乎不额外绕路；
3. `main`/`any` 都会让挂机主动绕去锻造房，代价超过武器 +25% 的收益。

### 这条结论同时修正了「钱花在武器上」那条规律

入侵模式里「钱买武器」有效，是因为**商店就在波次之间、不需要跑图**（零机会成本）。
探索模式里锻造需要跑图（有高机会成本）——**同样是「钱变武器等级」，结论相反**。

**规律要加限定：只有当「把资源变成战力」的机会成本接近 0 时，这条才成立。**

### 后续方向（明确不再走的路）

不再在「锻造/买什么」上做文章。探索侧的瓶颈是**清房效率**本身，下一轮应从

「血清数量」是当前最有解释力的变量（12 vs 2.9），所以应该**直接优化血清获取**：
1. 统计每层实际拿到几个棱镜 vs `ORB_CAP`（4）——若远低于 4，说明漏拿；
2. 让挂机**在 Boss 之前把本层能清的房间清完**（`late` 的完整版：不仅看 combat 房，
   还要看"本层棱镜是否已拿满"作为硬条件）。

原始数据：`docs/data/classic-shard-corr.jsonl`。

## 51. 结论 36：把「追击漏网之敌」改成「有棱镜就先拿棱镜」——过层率不变（3/8）

### 诊断（新增 `orbs`/`prisms`/`shardN` 调试字段）

trace 显示一局在 t=345–366 期间：

```
obj="hunt"  note="清房：追击漏网之敌"  prisms=1  shardN=5  orbs="0/1"
```

**场上有 1 个未拾取的棱镜，而挂机在追一个追不到的敌人**（hunt 持续 20+ 游戏秒）。
结合 §50 的结论（血清 12 vs 2.9），这等于在扔掉最有价值的资源。

### 改动

`hunt` 持续超过 60 tick 且场上有棱镜时，**改为去拿棱镜**（`弃追：先去拿棱镜`）。

### 实测（8 种子，classic，goal-depth 2）

| 种子 | floor |
|---|---|
| 7 | **1** |
| 23 | **2** |
| 33 | **1** |
| 13 / 43 / 53 / 63 / 73 | 0 |

**过层率 3/8**，与基线（2–3/8）**无差别**。

### 诚实结论

- 这是一个**真实逻辑缺陷的修复**（追击无限期、棱镜被搁置），代码保留；
- 但它**没有提升过层率**——说明「追击卡住」不是主要瓶颈，或者拿到的额外棱镜还不足以跨越一层；
- 瓶颈仍在**总伤害**：血清拿了也不一定够（`ORB_CAP=4/层`，而绝境敌人血量 ×2）。

## 52. 结论 37：**累计血清数**与过层强相关（7.25 vs 3.5），而「每层棱镜产出」不是必要条件

### 实测（8 种子，classic，goal-depth 2，本轮 `orbs`/`shardN` 已入结果行）

| 种子 | 楼层 | orbs（本层）| shardN（累计）| 游戏秒 |
|---|---|---|---|---|
| 7 | **1（过层）** | 4 | **10** | 567 |
| 33 | **1（过层）** | 0 | **5** | 533 |
| 53 | **1（过层）** | 1 | **7** | 645 |
| 23 | **1（过层）** | 2 | **7** | 490 |
| 13 | 0 | 3 | 4 | 198 |
| 63 | 0 | 3 | 5 | 274 |
| 43 | 0 | 2 | 2 | 357 |
| 73 | 0 | 3 | 3 | 294 |

**过层率 4/8（50%）**，为本会话最高。

### 两个关键观察

1. **`orbs`（本层棱镜产出）不是必要条件**——种子 33 的 `orbs=0` 也过层了。
   因为 `G.floorOrbs` 是**按层计数、跨层归零**，它反映的是「最后一层拿了几个」，不代表累计成长；
2. **`shardN`（累计血清）才是强相关量**：
   - 过层组均值 **7.25**
   - 不过层组均值 **3.5**
   - **约 2 倍差异**，与 §50 的 12 vs 2.9 方向一致。

### 修正 §51 的判断

之前说「瓶颈是总伤害」没错，但更精确地说：**是累计血清数（伤害成长）**，
而不是「每层拿满 4 个棱镜」这个具体的产出指标。

### 因此下一步该做什么

不要再去优化「每层棱镜产出」，而要**提高血清获取效率**：
1. 棱镜出现后**优先去开**（`orbOpen` 状态，需要 E 或点击）；
2. 商店的 `shard` 类商品**优先买**（`it.what === 'shard'`，现在已经会买，但评分门槛 `>= 2` 可能过高）；
3. 选卡时**优先有伤害成长的血清**（`POLICY_W` 已按流派加权，但可以全局提高伤害类权重）。

原始数据：`docs/data/classic-orb-shard.jsonl`。

## 53. 结论 38：降低商店血清门槛是**明确有害**（0/8 vs 4/8）

动机：§52 发现累计血清数与过层强相关（7.25 vs 3.5），于是想把商店买血清的门槛
从 `scoreShard >= 2` 降到 `>= 1`，多买血清。

| 配置 | 过层率（8 种子）|
|---|---|
| `shopShardBar=2`（默认）| **4/8 = 50%** |
| `shopShardBar=1`（多买血清）| **0/8 = 0%** |

**结论：降门槛是明确有害的，默认保持 2。** 可配置项保留（`A.opts.shopShardBar`）。

### 机制：墨水是零和资源，替代用途比绝对数量重要

降低门槛看似「多拿成长」，实际是**把墨水从武器挤出去**：

- 武器是伤害**基数**（`w.dmg[t] × sc`），每级 +25%；
- 低价值血清只给少量 `dmg%`，在武器基数不足时几乎无效；
- 结果：血清数量变多，但**总伤害反而更低** → 一层都过不去。

这与 §43（锻造绕路有害：跑图成本 > +25% 收益）和 §47（入侵「只买武器」有效）
形成**一致的规律**：

> **资源分配的第一原则是「先保证基数（武器），再谈加成」。**
> 无论探索还是入侵、买还是锻造，违反这条都会变差。

| 改动 | 结果 | 判定 |
|---|---|---|
| 导航兜底修复 | 过层率 0/5 → 3/5 | ✔ 有效 |
| `clear-first`（不折返捡棱镜）| 0/8 vs 3/8 | ✘ 有害 |
| `forgeMode=any/main`（多去锻造）| 0/5（两种）| ✘ 有害 |

| 追击改拿棱镜 | 3/8（无变化）| — 修复缺陷，无收益 |

**规律非常一致：任何「增加非武器投入」的改动都会变差；只有修复机械缺陷才有效。**
